Rust × AI 활용 지도

AI 덕분에 코드를 쓰는 비용은 크게 낮아졌고, 남는 비용은 그 코드가 맞는지 확인하는 쪽으로 옮겨가고 있습니다 추론. Rust는 그 확인의 큰 부분을 컴파일러가 강제하는 언어입니다. 그래서 둘의 조합은 "Rust 배우기가 쉬워졌다"보다 "검증 비용이 싸지는 개발 방식"으로 볼 때 실익이 큽니다.

핵심 판단

1

"Rust가 대중화되지 못했다"는 절반만 맞습니다 문서

2025 State of Rust 설문(2026년 3월 발표)에서 "소속 조직이 Rust를 의미 있게 쓴다"고 답한 응답자는 48.8%였습니다. 2023년 38.7%, 2024년 45.5%에서 계속 올랐지만 오름폭은 줄었습니다. 응답자 대부분이 이미 Rust를 쓰는 사람이므로 "전체 기업의 절반"으로 읽으면 안 됩니다. 리눅스 커널은 2025년 12월 Rust 실험 단계를 마치고 계속 유지하기로 결론 냈고(아직 기본 빌드에는 포함되지 않음), 안드로이드에서는 2025년 1~3분기 시스템 언어로 새로 늘어난 자체 코드 줄 수에서 Rust가 C++와 맞먹는 수준까지 왔습니다. 같은 설문에서 응답자의 가장 큰 걱정 두 가지는 "업계에서 충분히 쓰이지 않는다"(42.1%)와 "언어가 너무 복잡해진다"(41.6%)였습니다. 쓰는 곳은 늘고 있지만, 쓰는 사람들조차 확산을 체감하지 못하는 상태입니다.

2

AI는 쓰는 비용을 낮췄고, 병목은 검증으로 옮겨갑니다 추론

Rust의 진입 장벽이던 "빌림 검사기와 씨름하는 시간"은 이제 에이전트가 대신 씁니다. 하지만 사람은 여전히 그 코드가 맞는지 판단해야 합니다. 여기서 언어마다 차이가 납니다. 같은 실수를 Python은 운영 중에, C++는 정의되지 않은 동작으로, Rust는 컴파일 단계에서 드러내는 경우가 많습니다. AI가 쓰는 코드가 많아질수록 기계가 대신 확인해 주는 범위가 넓은 언어가 유리해집니다.

3

사람이 쓴 Rust에서는 효과가 측정돼 있습니다 문서

구글은 안드로이드에서 Rust의 메모리 안전 취약점 밀도가 C/C++보다 약 1000배 낮고, 중대형 변경의 롤백률은 약 4배 낮으며, 코드 리뷰 시간은 약 25% 짧다고 보고했습니다(2025년 11월). 다만 1000배는 Rust 약 500만 줄에서 나온 잠재 취약점 1건을 과거 C/C++ 밀도와 비교한 추정치이고, 리뷰 시간 단축은 구글 스스로 팀의 Rust 숙련도 상승 덕일 수 있다고 봅니다. 마이크로소프트의 RustAssistant는 LLM과 컴파일러를 반복시켜 실제 저장소의 Rust 컴파일 오류를 최고 약 74%까지 고쳤습니다. 이는 컴파일되게 만든 비율이지 동작이 맞다는 뜻은 아니며, GPT-4 시절 결과입니다. AI가 쓴 Rust에서도 같은 효과가 나는지는 아직 직접 근거가 부족합니다 추론.

4

AI가 Rust에서 자주 틀리는 지점은 따로 있습니다 문서

RustEvo² 연구(2025년 3월, 당시 모델 기준)에서 LLM의 정답률은 학습 시점 이전 API 56.1%, 이후 API 32.5%였고, 검색 보강을 붙이면 평균 13.5%p 올랐습니다. 시그니처는 그대로인데 의미만 바뀐 API에서는 38.0%로 떨어졌습니다. 저장소 단위 이슈 해결 연구에서는 컴파일 실패의 원인이 저장소 전체 구조와 타입·트레이트 규칙을 놓치는 데 있었습니다. 그리고 컴파일 통과와 좋은 코드는 별개입니다. 빌림 검사기를 .clone()이나 Arc<Mutex>로 달래는 코드도 컴파일은 됩니다.

5

그래서 할 일은 검증 루프를 갖추는 것입니다 추론

컴파일러가 못 잡는 나머지(Rust다운 코드인지, 동작이 맞는지, 의존성이 안전한지, 최신 API인지)를 린트·테스트·의존성 검사·소스 열람으로 자동 확인하게 만들면, 사람의 리뷰는 설계 판단에 집중할 수 있습니다. 이 페이지와 함께 전달한 rust-ai-harness가 그 구성입니다.

왜 맞물리는가: 버그가 어디서 잡히나

AI가 쓴 코드에서 아래 표의 컴파일 칸은 사람이 리뷰하기 전에 에이전트의 편집 루프 안에서 드러나는 결함입니다. 다만 에이전트가 그 오류를 unwrap, clone, _ 와일드카드로 덮어버릴 수 있어서, 린트와 리뷰가 함께 있어야 의미가 있습니다. 나머지 칸은 테스트나 운영, 사람의 눈에 의존합니다.

출발점 세션의 실측

하네스와 예제를 만들면서 실제로 일어난 일입니다. 잘된 것과 함께, 컴파일러가 못 잡은 것과 제 추론이 틀린 것도 남겼습니다. 환경: 클라우드 샌드박스, x86_64 2 vCPU, rustc·cargo 1.99.1, clippy 1.99, PyO3 0.30.1, CPython 3.13.18. PyO3·unsafe·Cargo·린트·벤치 항목은 별도의 검토 에이전트가 같은 환경에서 다시 재현했습니다.

기억과 현재 확인

PyO3 0.30.1에는 allow_threads가 없습니다

학습 기억대로 썼다면 GIL 해제에 py.allow_threads를 써서 컴파일 오류가 났을 겁니다. 잠긴 버전의 레지스트리 소스와 CHANGELOG를 먼저 열어, 0.26.0(2025-08-29)에서 detach로 이름이 바뀌며 옛 이름은 폐기 예정이 됐고 0.28.0(2026-02-01)에서 제거된 것을 확인한 뒤 썼습니다. 이름 변경은 컴파일러가 잡아주는 쉬운 경우입니다. 시그니처가 같고 의미만 바뀐 API는 조용히 틀리므로, 소스를 직접 확인하는 습관이 더 중요해집니다.

컴파일러의 한계 확인

메모리 누수는 컴파일을 통과했습니다

예제 파서의 into_owned()를 처음 쓸 때 'static 수명을 맞추려고 Box::leak을 썼습니다. 컴파일도 테스트도 통과하는 코드였고, 커밋 전 자체 검토에서 발견해 키도 Cow로 바꾸는 설계로 고쳤습니다. 안전한 Rust에서도 누수는 허용됩니다. 이 패턴은 리뷰어 서브에이전트의 점검 목록에 넣었습니다.

추론이 틀림 확인

PyO3 브리지도 forbid(unsafe_code)로 빌드됩니다

"매크로가 unsafe를 생성하니 deny로 낮춰야 한다"고 추론해 설정했다가, 실제로 forbid로 빌드해 보니 통과했고 직접 쓴 unsafe 블록만 정확히 거부됐습니다. 설정을 forbid로 되돌리고 이 과정을 설계 기록에 남겼습니다.

린트 확인

clippy 도움말은 스스로 #[allow]를 권합니다

pedantic 린트가 걸리면 clippy는 "#[allow(...)]를 추가하라"는 도움말을 함께 냅니다. 에이전트가 이걸 그대로 따르면 린트가 무력화됩니다. 하네스는 #[allow] 자체를 경고로 만들고, 이유를 단 #[expect]만 허용합니다. 억제가 필요 없어지면 컴파일러가 알려주므로 저절로 정리됩니다. 또 allow-expect-in-tests 설정은 테스트 파일 안의 헬퍼 함수에는 적용되지 않는다는 것도 확인했습니다.

Cargo 확인

워크스페이스 exclude는 glob을 처리하지 않습니다

exclude = ["bridges/*"]로는 브리지가 제외되지 않아 maturin 빌드가 실패했습니다. 브리지마다 빈 [workspace]를 두는 방식으로 해결했습니다.

적대적 검토 확인

독립 검토 에이전트가 하네스의 구멍을 찾았습니다

작성자가 "검증 완료"로 여겼던 첫 버전에서, 반박 관점으로 붙인 별도 에이전트가 실제 실험으로 네 가지 큰 구멍을 재현했습니다. 턴 중에 커밋하면 종료 게이트를 통과했고, 해시 도구가 없으면 게이트가 꺼졌고, Python 브리지는 모든 로컬 검사 밖에 있었습니다. 또 자동 허용 규칙에 걸리는 형태의 cargo test에 --config를 붙여 임의 명령을 실행할 수 있었습니다(실행 자체는 실측, 확인 창 없이 통과하는지는 문서 기준 판단). 모두 근본 원인을 고쳤습니다. 같은 검토에서 속성 테스트가 제어 문자를 만들지 않아, 일부러 넣은 이스케이프 결함 두 개를 놓친다는 것도 드러났고, 생성기를 바꿔 둘 다 잡히게 했습니다. 수정본을 다시 검토하자 수정이 만든 회귀(이식한 저장소에서 포맷 훅이 거짓 오류를 냄)와 통과는 하지만 아무것도 증명하지 않는 훅 테스트가 나왔고, 마지막으로 새 검토 에이전트가 빈 저장소에서 첫 커밋으로 게이트를 우회하는 경로와 정책 검사의 회귀를 더 찾았습니다. 모두 고친 뒤 보호 장치를 일부러 제거한 변형 훅으로 돌려 각 테스트가 실제로 실패하는 것을 확인했고, 지금 훅 동작은 저장소 사본에서 도는 {{fig:hooktests.n}}(scripts/test-hooks.sh)로 고정돼 있습니다. 라운드별 기록은 검증 기록에 있습니다. 실제 Claude Code 세션 안에서의 훅 동작은 아직 확인하지 않았습니다 미확인.

빌드 캐시 확인

빌드 디렉터리를 공유하면 검증이 남의 산출물로 통과합니다

훅 테스트를 저장소 사본에서 돌리며 원본과 같은 CARGO_TARGET_DIR을 썼더니, 원본의 검증이 사본의 수정된 소스로 만든 산출물과 경고를 그대로 재사용했습니다. 병렬 세션이나 worktree를 많이 쓴다면 전역 CARGO_TARGET_DIR을 공유하지 마세요. 하네스는 세션 시작 때 이 설정이 작업 사본 밖을 가리키면 경고합니다.

확인 30만 줄 logfmt 로그에서 level 값 집계. 한 번 실행할 때 5회 중 최솟값을 쓰고, 이를 6번 실행(작성 3번, 독립 검토 3번)한 범위입니다. 세 구현의 결과가 같은지 벤치 안에서 단언한 뒤 쟀습니다. 실행별 배율은 정규식 버전 대비 7.2~9.8배, 루프 버전 대비 12.0~17.2배였습니다. 막대 길이는 작성 때 3번 실행의 중앙값(2214 · 1269 · 131 ms) 기준입니다. 기계와 데이터에 따라 달라지므로 자기 환경에서 다시 재야 합니다.

어디에 쓸까

AI가 Rust 작성 비용을 낮춰도 운영·채용·장애 대응 같은 조직 비용은 그대로입니다. 그래서 경계가 좁고, 이득을 숫자로 증명할 수 있고, 실패해도 되돌리기 쉬운 곳부터 시작하는 것이 맞습니다 추론. 회사 환경은 여기서 알 수 없어 가정하지 않았습니다. 아래 표는 개인 작업에서 먼저 검증한 뒤 회사 적용을 판단할 때 쓰는 기준입니다.

대상적합도이유시작점
개인 CLI·개발 도구최적위험이 낮고 단일 바이너리로 배포가 쉽다. 학습 효과가 가장 크다.clap + anyhow, 예제 crates/logq
개인 MCP 서버·에이전트 도구최적AI 도구를 많이 쓰는 개발자에게 바로 쓸모가 생긴다. 공식 Rust SDK가 있다.rmcp 3.8.0 확인
Python·Node 서비스의 CPU 핫스팟적합경계가 함수 하나로 좁고, 전후 측정으로 효과를 증명할 수 있다.PyO3 + maturin(예제 bridges/py-logq), Node는 napi-rs
파서·프로토콜·신뢰할 수 없는 입력 처리적합메모리 안전에 proptest·퍼징을 더하면 이득이 가장 크다.logq-core 패턴 + proptest
신규 고성능 네트워크 서비스조건부async 복잡도와 운영 역량(관측, 장애 대응)이 필요하다. 팀이 함께 읽을 수 있어야 한다.axum + tokio, 작은 내부 서비스부터
기존 C/C++ 대규모 이식조건부테스트 자산이 전제다. 자동 번역은 아직 연구 단계에 가깝다. C→safe Rust 벤치에서 o3가 테스트 기반 3회 수정으로 48%, 한 번에는 19%(2025) 문서.모듈 하나를 FFI 경계로 감싸 교체
일반 CRUD 백엔드 (JVM·TS 팀)비추천성능·안전 이득이 작고 조직 비용이 크다.기존 스택 유지
ML 연구 코드·노트북, UI 중심 프론트비추천생태계와 반복 속도는 Python·TS가 압도한다. 핫스팟만 떼어내는 것은 예외.위 핫스팟 브리지

하네스: rust-ai-harness

출발점 세션에서 만든 Rust 작업 하네스입니다. 새 프로젝트의 템플릿으로 쓰거나 기존 Rust 저장소에 이식할 수 있습니다. 전체 게이트(정책 검사, fmt, clippy -D warnings, {{fig:gate.tests}}, Python 브리지, rustdoc, cargo-deny)와 {{fig:hooktests.n}}가 통과했습니다 확인.

AOK에는 ⑧ 작업 레포 하네스(제안 D20)로 들어옵니다. 훅·게이트·단일 진입점·리뷰어를 언어 중립 코어로 두고, Rust는 그 위의 어댑터가 됩니다. 아래 구성은 지금의 Rust 판입니다 추론.

AGENTS.md / CLAUDE.md   # 에이전트 규칙: 도구 중립 본문 + Claude Code 전용 부분(@AGENTS.md 임포트)
Cargo.toml              # [workspace.lints]: pedantic + AI가 자주 새는 패턴 선별, unsafe forbid
scripts/verify.sh       # 단일 게이트 policy | light | static | fast | full: 사람·에이전트·CI 공용, bridges/* 포함
scripts/test-hooks.sh   # 훅 회귀 테스트 30개: 저장소 사본에서 모의 입력으로 실행, CI 에서도
.claude/settings.json   # 의존성·정책·게이트 파일 변경과 cargo --config 류는 확인(ask), publish 차단, 훅 4개
.claude/hooks/          # 세션 시작 버전 주입 · 편집 직후 check · 턴 종료 verify
.claude/agents/         # rust-reviewer: 적대적 리뷰 서브에이전트
deny.toml               # 취약점·라이선스·출처 게이트
.github/                # CI(같은 verify.sh) + Dependabot(cargo, actions)
crates/logq-core        # 기준 예제: 입력을 빌리는 파서, Cow, thiserror, proptest
crates/logq             # CLI 예제: 파이프가 닫혀도 패닉하지 않는 출력, anyhow
bridges/py-logq         # 같은 코어를 Python 확장으로 + 결과 일치를 단언하는 벤치
docs/decisions.md       # 결정 12개의 근거·미확인 사항, 아직 켜지 않은 도구(씨앗) 10개

설계의 축

  • 규칙의 출처는 하나: 로컬·에이전트·CI가 같은 verify.sh
  • 편집 직후는 가볍게(오류만), 턴 종료는 엄격하게(fmt·clippy·테스트)
  • 실패는 숨기지 않는다: 3회 막힌 뒤에는 "보고"를 강제하고 풀어준다
  • 실패 테스트를 먼저 쓸 때와 학습 모드에서만, 이유를 남기고 그 턴의 컴파일 오류·테스트 실패를 허용한다(정책·포맷은 그대로, 사용자에게 알림)
  • 학습 기억보다 현재: 세션마다 실제 rustc 버전과 의존성 소스 경로를 주입
  • 스스로 정리: #[expect], Dependabot, 그리고 하네스 자신을 시험하는 훅 회귀 테스트
  • 권한 규칙은 실수를 막는 가드레일입니다. 실제 격리는 클라우드 세션의 VM이나 샌드박스가 맡습니다

함정과 대응

에이전트와 Rust를 함께 쓸 때 반복해서 나오는 문제와, 하네스나 습관으로 막는 방법입니다.

타입부터 리뷰하기

Rust에서는 타입과 함수 시그니처가 설계의 대부분을 담습니다. 구현 전에 "타입·트레이트·공개 함수 시그니처만 먼저 제안해"라고 시키고 그 부분만 리뷰하세요. 상태는 enum으로, 검증된 값은 newtype으로 표현하게 하면 이후 구현의 일관성은 컴파일러가 지킵니다.

효과 리뷰 대상이 수백 줄 구현에서 수십 줄 타입으로 줄어듭니다 추론

빌림 검사기 달래기

오류를 빨리 없애려고 .clone(), Rc<RefCell>, Arc<Mutex>, Box::leak을 쓰는 경향이 있습니다. 컴파일은 되지만 성능이 떨어지고 구조가 망가집니다. 린트로는 일부만 잡힙니다.

대응 AGENTS.md 규칙(구조부터 고치고, 복제하면 이유 보고) + 리뷰어 점검 목록

낡은 API

크레이트 API는 학습 이후에도 바뀝니다. 이름이 바뀐 API는 컴파일 오류로 드러나지만, 시그니처는 같은데 의미가 바뀐 API는 조용히 틀립니다(RustEvo²에서 정답률 38.0%).

대응 Cargo.lock 버전의 ~/.cargo/registry/src 소스를 직접 열람. 세션 시작 훅이 경로를 알려줍니다

"컴파일됐으니 끝"

타입은 논리를 증명하지 않습니다. 에이전트가 쓴 테스트는 손으로 고른 예시만 확인하는 경우가 많습니다.

대응 파서·변환에는 proptest 규칙, 테스트가 정말 무언가를 잡는지 의심되면 cargo-mutants(씨앗 S3)

억제 남발

린트가 많아지면 에이전트는 #[allow]로 빠져나가려 합니다. clippy 도움말도 그렇게 권합니다.

대응 allow_attributes 경고 + 이유 필수 #[expect] + 턴 종료 훅 메시지가 "억제하지 말라"고 명시

async의 숨은 비용

async 안의 블로킹 호출, .await 너머로 들고 가는 락, 상한 없는 채널은 컴파일되지만 운영에서 터집니다.

대응 필요해질 때까지 동기 코드로. 도입하면 AGENTS.md async 규칙과 리뷰어가 점검

컴파일 시간과 루프 비용

설문에서 여전히 상위 불만입니다. 에이전트 루프에서는 기다리는 시간이 곧 비용입니다. Rust 프로젝트는 2026년 목표로 병렬 프런트엔드, Cranelift 백엔드, "재빌드 대신 재링크(RDR)" 등을 추진하고 있습니다 문서.

대응 편집 루프는 cargo check만, 테스트는 턴 종료 시 한 번. 느려지면 링커·캐시(씨앗 S7)

병렬 세션과 빌드 캐시

세션 여러 개나 worktree로 병렬 작업할 때 빌드 디렉터리를 공유하면, 한 사본의 산출물로 다른 사본의 검증이 통과할 수 있습니다(출발점 세션에서 실제로 겪음).

대응 사본마다 기본 target/을 쓰고 전역 CARGO_TARGET_DIR은 두지 않기. 세션 시작 훅이 경고

unsafe 생성

성능이나 FFI를 이유로 에이전트가 unsafe를 제안할 수 있습니다. 불변식을 아무도 이해하지 못한 unsafe는 안전 보장을 무너뜨립니다.

대응 전역 forbid. 필요하면 구현 전에 제안 → 승인 → 별도 크레이트로 격리 + // SAFETY: + Miri

4주 계획

시니어 개발자에게 필요한 것은 Rust 문법 암기보다 AI가 쓴 Rust를 판정할 수 있는 눈입니다. 아래 순서는 그 눈을 기르면서 쓸모 있는 결과물도 남기도록 짰습니다 추론.

직접 판단할 것

  • 타입·모듈 경계, 소유권을 누가 갖는지
  • 공유 상태와 동시성 구조
  • unsafe와 의존성 추가 여부
  • 테스트가 무엇을 증명하는지

맡겨도 되는 것

  • 보일러플레이트, serde·clap 연결, FFI 글루 코드
  • 컴파일 오류 해석과 1차 수정
  • 테스트 초안, proptest 전략 작성
  • 벤치마크와 결과 일치 검증 코드
1주차

소유권·빌림·수명을 예측하며 익히기

  • 학습 모드로 logq-core를 읽으며, 코드를 바꾸기 전에 컴파일 결과를 먼저 예측하고 맞춰보기
  • The Rust Book 4장(소유권), 10장(제네릭·트레이트·수명)을 에이전트 설명과 함께
  • 일부러 Box::leak, 불필요한 clone을 넣고 리뷰어가 잡는지 보기

완료 기준: 빌림 오류 메시지를 보고 원인과 해결안 두 가지를 스스로 말할 수 있다

2주차

개인 도구 하나를 하네스 위에서

  • 평소 쓰는 셸 스크립트나 Python 스크립트 하나를 CLI로. 타입 설계는 직접, 구현은 에이전트
  • 오류 처리 경계 연습: 라이브러리는 thiserror, 바이너리는 anyhow
  • 또는 자주 쓰는 개인 작업용 MCP 서버를 rmcp로

완료 기준: verify.sh full 통과, 매일 실제로 쓴다

3주차

핫스팟 하나를 숫자로 증명하기

  • 후보 예: docbench diff(WASM) 또는 work-atlas 유사도 질의(독립 CLI — PyO3는 이득이 작음). 적용 사례의 프로토타입에서 시작
  • 먼저 언어를 바꾸지 않는 수정(1단계)을 적용·측정하고, 그 뒤에도 남는 비용에만 Rust를 씁니다. 결과 일치 단언과 전후 측정을 함께

완료 기준: 같은 결과, 측정된 개선 수치, 되돌리는 방법이 문서에 있다

4주차

동시성 기초와 리뷰하는 눈

  • Send/Sync, 스레드, 필요하면 tokio 기초. 동기 버전과 비교
  • 에이전트가 쓴 변경을 리뷰어 점검 목록으로 직접 리뷰하고, 리뷰어 서브에이전트 결과와 비교
  • 한 달 회고는 체감 대신 기록(소요 시간, 막힌 지점, 실패 횟수)으로. docs/decisions.md 갱신

완료 기준: 회사 적용을 제안할지 판단표 기준으로 결정할 수 있다

체감과 실제는 다를 수 있습니다 문서. METR의 2025년 초 실험(숙련 개발자 16명, 익숙한 대형 저장소)에서 AI를 쓴 작업은 19% 더 오래 걸렸지만 참가자들은 20% 빨라졌다고 느꼈습니다. 2025년 하반기 후속 실험(2026년 2월 발표)에서는 같은 참가자 10명이 18%, 새 참가자 47명이 4% 빨라진 것으로 추정됐지만 신뢰구간이 0을 포함합니다. METR은 지금은 더 빨라졌을 가능성이 높다고 보면서도, AI 없이 일하기를 거부하는 개발자가 늘어 그 크기를 제대로 잴 수 없다고 밝혔습니다. 그래서 기록으로 회고하는 습관이 필요합니다.

반론과 남는 위험

"AI가 다 써주면 언어는 상관없다"

  • 쓰기만 놓고 보면 맞는 말입니다. 하지만 읽고 판정하는 비용은 언어마다 다르고, AI가 많이 쓸수록 그 차이가 커집니다 추론
  • 팀이 이미 강한 스택에서 얻는 이득이 크다면 바꿀 이유는 약합니다

Rust는 AI에게도 어려운 언어

  • 학습 데이터가 Python·TS보다 적고, 최신 API·저장소 구조·C→Rust 번역에서 정답률이 눈에 띄게 낮습니다 문서
  • 컴파일 시간 때문에 에이전트 반복 한 번이 더 길어집니다. 검증이 싸지는 만큼 작성은 비싸질 수 있습니다 추론

이해 부채

  • 에이전트가 쓴 Rust를 아무도 깊이 이해하지 못한 채 쌓이면, 장애 때 아무도 고치지 못합니다
  • 그래서 계획의 중심이 판정하는 눈입니다
