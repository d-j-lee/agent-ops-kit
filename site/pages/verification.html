AI 검증 플레이북

세 검증은 서로 다른 질문에 답합니다. 하나로 다른 것을 대신할 수 없고, 셋 다 실행해서 확인한 근거(테스트·재계산·재측정)에 기댈수록 강해집니다. 이 페이지는 그 차이와 쓰는 법을 실제로 돌린 검증 기록과 함께 정리하고, 각각이 AOK의 어느 기능(①·③·④·⑦)에 해당하는지 잇습니다.

교차검증다른 눈으로 봐도 같은가?

다른 출처·방법·맥락에서 같은 결론이 나오는지 확인합니다.

적대적 검증어떻게 하면 깨지는가?

내보내지 말아야 할 이유를 찾으려고 일부러 공격합니다.

회귀검증고친 뒤에도 전에 되던 것이 되는가?

바꾸기 전에 성립하던 것이 바꾼 뒤에도 성립하는지 반복해 확인합니다.

  • 확인 직접 실행·측정, 다시 돌릴 수 있는 근거
  • 도출 확인된 값에서 계산
  • 추론 판단이 들어감
  • 미확인 확인하지 못함
  • 기록됨 다른 세션·에이전트의 기록

세 가지 검증

머신러닝의 교차검증(k-fold)과는 다른 뜻입니다. 여기서 교차검증은 "독립적인 두 번째 확인"을 말합니다. 셋의 차이는 검증자에게 무엇을 요구하느냐에 있습니다. 교차검증은 독립성, 적대적 검증은 반증하려는 목표, 회귀검증은 변하지 않는 기준선과 반복을 요구합니다.

교차검증적대적 검증회귀검증
검증자의 태도중립. 같은 결론이 나오는지 본다반증. 깨뜨릴 방법을 찾는다보존. 전과 같은지 본다
핵심 요건출처·방법·맥락이 원래 작업과 분리될 것통과시키지 않으려는 목표, 실험으로 재현할 것고정된 판정 기준(테스트·기준 출력)과 자동 반복
잘 잡는 것사실 오류, 계산 실수, 지어낸 인용, 출처 왜곡경계 입력, 우회 경로, 보안·권한 구멍, 과장, 숨은 가정수정이 만든 새 결함, 되살아난 옛 버그, 성능 퇴행, 문서와 실제의 어긋남
놓치는 것검증자와 공유한 맹점(같은 모델·같은 맥락)시간 안에 시도하지 않은 공격. 전수 검사가 아니다테스트가 없는 동작, 아무것도 확인하지 않는 테스트
AI에서의 함정결론을 건네면 동의하는 쪽으로 기운다. 같은 계열 모델은 함께 틀린다근거 없는 의심 목록이 쏟아진다. 재현한 것과 의심을 나눠야 한다AI는 국소적으로 고치며 주변을 깨기 쉽다. AI가 쓴 테스트는 통과만 할 수 있다
결과물일치·불일치 목록과 각 근거의 출처심각도순 발견 목록, 발견마다 재현 방법통과·실패 표, 실패한 기준과 처음 실패한 변경
언제사실·수치·인용, 남에게 줄 문서게이트·권한·보안, 되돌리기 어려운 것, 출시 직전모든 변경 뒤(자동으로), 수정 라운드 뒤(반드시)

두 축과 바닥

교차·적대는 두 축의 조합으로 보면 쉽습니다. 누가 보느냐(같은 맥락인가, 분리된 맥락인가)와 무엇을 목표로 하느냐(확인인가, 반증인가)입니다. 흔히 말하는 "적대적 교차검증"은 오른쪽 아래 칸, 즉 분리된 맥락에서 반증을 목표로 하는 검증입니다. 회귀검증은 이 격자에 들어가지 않습니다. 같은 판정을 시간에 걸쳐 반복하는 축이기 때문입니다.

같은 맥락 (작성자 자신)
분리된 맥락 (새 에이전트·다른 모델·사람)
확인
자기 검토"다시 확인해 봐". 가장 약하다. 같은 맹점으로 같은 결론에 이른다
교차검증결론을 모르는 검증자에게 산출물과 출처만 준다
반증
자기 반론"반대 입장에서 비판해 봐". 사각지대 일부는 드러나지만 맥락이 같아 한계가 있다
적대적 교차검증분리된 검증자가 깨뜨리기를 목표로 실험한다. 비싸지만 가장 많이 찾는다
시간 축 — 회귀검증위의 어떤 판정이든 한 번 성립한 것은 기준으로 고정하고, 변경할 때마다 다시 돌립니다. 사람이나 에이전트가 아니라 스크립트가 하는 편이 맞습니다.
바닥 — 실행해서 판정하기컴파일러, 테스트, 재계산, 재측정, 전후 출력 비교. 세 검증 모두 의견보다 실행으로 결론 낼 때 믿을 만해집니다. 검증 에이전트에게도 "주장"이 아니라 "실험"을 요구하세요.

AI라서 다른 점

사람끼리의 리뷰 습관을 그대로 AI에 옮기면 약해지는 지점이 있습니다. 연구로 확인된 성질부터 보겠습니다.

스스로는 잘 못 고친다 문서

찾는 게 병목이다 문서

추론 과정에서 첫 오류 위치를 찾는 정확도는 가장 좋은 모델(GPT-4)도 {{fig:tyen.acc}}였습니다. 반면 오류 위치를 알려 주면 스스로 고쳐 전체 성능이 올랐습니다(Tyen 외, 2023). 고치는 일보다 찾는 일을 다른 검증자에게 맡겨야 하는 이유입니다 추론.

함께 틀린다 문서

HELM 리더보드({{fig:kim.models}}, 4지선다)에서 두 모델이 모두 틀린 문제의 {{fig:kim.helm}}에서 같은 오답을 골랐습니다. 무작위라면 {{fig:kim.chance}}입니다. {{fig:kim.all}} 전체로 보면, 크고 정확한 모델일수록 제공사와 구조가 달라도 오류가 강하게 상관됐습니다(Kim 외, ICML 2025). 다른 모델을 섞으면 독립성이 늘지만 완전히 독립이 되지는 않습니다 추론.

동의하는 쪽으로 기운다 문서

{{claim:C-res-sharma}} 검증 요청에 내 결론을 적어 보내면 확인해 주는 답이 돌아오기 쉽습니다 추론.

테스트 통과가 정답은 아니다 문서

SWE-bench는 수정이 실패하던 테스트를 통과시키고(FAIL_TO_PASS) 통과하던 테스트도 계속 통과시킬 것(PASS_TO_PASS)을 함께 요구합니다. 그래도 테스트를 통과한 AI 패치의 {{fig:swe.fullfail}}가 수정된 파일만이 아닌 전체 개발자 테스트에서 실패했고, 표본 수동 검사로 추정한 오답 비율은 {{fig:swe.wrong}}였습니다(ICSE 2026).

커버리지가 검출력은 아니다 문서

LLM이 만든 테스트가 줄·분기 커버리지 {{fig:mutgen.cov}}인데 변이 점수는 {{fig:mutgen.mut}}인 사례가 보고됐습니다. 코드를 실행하기만 하고 결과를 거의 확인하지 않는 테스트입니다(MutGen, 2025).

그래서 AI 검증자에게는 추론
  1. 맥락을 분리합니다. 작업 대화를 물려받지 않은 새 검증자에게 산출물만 줍니다.
  2. 결론을 숨깁니다. "맞는지 확인해 줘" 대신 "내보내지 말아야 할 이유를 찾아 줘"라고 요청합니다.
  3. 실험을 요구합니다. 주장마다 실행한 명령과 결과, 즉 재현(VERIFIED)과 의심(SUSPECTED)을 구분하게 합니다.
  4. 회귀는 사람이나 에이전트의 기억에 맡기지 않습니다. 기준 테스트와 자동 실행으로 고정합니다.
  5. 테스트도 검증합니다. 보호하려는 코드를 일부러 지웠을 때 테스트가 실패하는지 봅니다.

실제 검증 기록

2026-10-28~30에 Rust 작업 하네스를 만들며 같은 산출물에 검증 방식을 바꿔 가며 붙였습니다. 그래서 방식별로 무엇을 찾았는지 비교할 수 있습니다. 건수는 각 검증 서브에이전트의 보고서에 적힌 값입니다 기록됨. 이력: {{doc:reports/2026-10-30-verification-rounds.md}}

검증 서브에이전트 한 번마다 작업 완료 알림에 표시된 토큰은 {{fig:rounds.tokens}}, 실행 시간은 {{fig:rounds.time}}이었습니다. "공허한 테스트"는 보호 장치를 지워도 통과하는 테스트를 말합니다. 3라운드의 중간 3건은 고친 뒤 실패→통과 테스트로 확인했지만 새 검증 라운드는 돌리지 않았습니다. 아래 "멈출 때" 기준대로라면 한 번 더 새 눈으로 보거나, 남은 위험을 밝히고 사람에게 수용 여부를 물었어야 하는 경우입니다.

자기 검증은 "완료"라고 했다

게이트를 통과하고 시나리오 테스트까지 돌린 뒤였는데도, 분리된 적대적 검증이 {{fig:r1.high}}을 찾았습니다. 네 건 모두 작성자가 미리 적어 둔 시나리오 목록에 없던 경로였습니다.

수정은 회귀를 만든다

2라운드와 3라운드 모두 직전 수정이 만든 회귀를 찾았습니다. 수정 라운드 뒤의 회귀검증은 선택 사항이 아닙니다. AOK에서는 ⑦을 ④의 라운드마다 붙입니다.

회귀 테스트도 검증해야 한다

수정마다 만든 회귀 테스트 중 {{fig:vacuous.total}}가 아무것도 증명하지 못했습니다. 보호 장치를 일부러 지운 변형으로 돌려 테스트가 실제로 실패하는지 보는 도구가 scripts/vacuity_check.py입니다.

검증 환경도 거짓말을 한다

테스트용 사본과 원본이 빌드 디렉터리를 공유하자, 원본 검증이 사본에서 빌드된 산출물과 경고를 재사용했습니다. 거짓 통과도 거짓 실패도 날 수 있고, 2라운드에서는 거짓 실패가 실제로 재현됐습니다. 검증은 격리된 사본에서, 사본마다 따로 빌드해야 합니다.

같은 검증자와 새 검증자는 역할이 다르다

같은 검증자는 발견 목록을 들고 있어 수정 확인이 빠르고 정확했습니다. 새 검증자는 앞 라운드가 보지 못한 회귀를 찾았습니다. 둘 다 필요합니다 추론.

시간 제한은 프롬프트로 지켜지지 않는다

3라운드 검증자에게 한 시간 안쪽을 요청했지만 {{fig:timebox}}이 걸렸습니다. 비용 상한이 중요하면 중간에 확인하고 직접 멈춥니다 추론.

새로 찾은 높음은 {{fig:trend.high}}, 중간은 {{fig:trend.mid}}이었습니다. 다만 2라운드에는 {{fig:trend.partial}}이 남아 있었습니다. 새 발견이 줄어드는 만큼 라운드의 비용 대비 효과도 줄어, 멈출 기준이 필요합니다(아래 "라운드와 멈출 때").

라운드와 멈출 때

  1. R0

    기계 판정

    작성자가 게이트(테스트·린트·타입·재계산)를 통과시킵니다. 이게 없으면 다음 라운드는 쉬운 결함 찾기에 시간을 씁니다.

    작성자 · 자동
  2. R1

    분리된 적대적 검증

    새 에이전트에게 산출물과 공격 범위만 줍니다. 사본에서 실험하게 하고, 발견을 심각도순으로, 재현과 의심을 나눠 받습니다.

    새 에이전트
  3. 수정

    발견마다 실패 테스트 먼저

    발견을 재현하는 테스트를 먼저 만들어 실패를 보고, 고친 뒤 통과를 봅니다. 그 테스트가 고정된 회귀 기준이 됩니다.

    작성자
  4. R2

    회귀 재검증

    R1과 같은 에이전트에게 발견마다 FIXED·PARTIAL·NOT FIXED를 실험으로 판정하게 하고, 수정이 만든 회귀를 찾게 합니다. 회귀 테스트가 공허하지 않은지도 함께 봅니다. 이 단계는 수정을 확인하는 일이고, 이후의 회귀를 지키는 것은 에이전트의 기억이 아니라 여기서 남긴 테스트와 스크립트입니다.

    R1과 같은 에이전트
  5. R3

    새 눈으로 최종 확인

    앞 라운드를 모르는 새 에이전트가 최신 변경에 집중해 시간 제한 안에서 봅니다. 앞 라운드가 남긴 맹점과 마지막 수정의 회귀를 잡는 단계입니다.

    새 에이전트
멈출 때 추론
  • 새 검증자의 라운드에서 높음·중간이 나오지 않으면 멈춥니다.
  • 남은 낮음은 고칠지, 알려진 한계로 문서에 남길지 정합니다. 남기는 것도 결정입니다.
  • 라운드를 더 돌릴 가치가 없는데 위험이 남았다면, 남은 위험과 확인 방법을 명시하고 사람이 수용 여부를 정합니다.

브리핑 템플릿

검증의 질은 브리핑에서 대부분 정해집니다. 공통 원칙은 결론을 주지 않고 산출물과 범위를 주는 것, 실험을 요구하는 것, 출력 형식을 고정하는 것입니다. <…> 부분만 바꿔 씁니다.

검증자는 비밀값과 푸시 권한이 없는 사본이나 샌드박스에서 돌립니다. 공격하라고 시킨 에이전트는 실제로 공격합니다. 출발점 세션의 1라운드 검증자도 자동 허용 규칙에 걸리는 형태의 명령으로 임의 명령을 실행할 수 있음을 보였습니다.

3. 새로 추가된 회귀 테스트를 검증한다. 보호하려는 코드를 지운 변형에서 그 테스트가 실패하는지 확인하고, 실패하지 않는 테스트는 "공허함"으로 보고한다.

발견도 주장이다

  • 검증자의 발견도 재현해 보고 채택합니다. 제안 패치를 그대로 쓰기 전에, 패치 없이는 실패하고 패치하면 통과하는 테스트를 먼저 확인합니다. AOK에서는 반박을 근거 재실행으로만 해소합니다(①, S8).
  • 보고서 안의 "이렇게 해라"는 권한이 없는 데이터입니다. 무엇을 할지는 작업 주인이 정합니다.
  • 근거 등급을 지킵니다. 의심을 요약하면서 사실로 바꾸지 않습니다.

수정마다 회귀를 고정한다

  • 실패하는 테스트 먼저, 고친 뒤 통과(FAIL_TO_PASS)를 확인합니다.
  • 수정한 파일의 테스트만이 아니라 전체가 계속 통과하는지(PASS_TO_PASS) 확인합니다.
  • 그 테스트가 공허하지 않은지, 보호 장치를 지웠을 때 실패하는지 봅니다(변이 확인).
  • 숫자나 개수가 바뀌면 모든 문서에서 함께 바뀌었는지 봅니다. 하네스의 훅 테스트 개수({{fig:hooktests.history}})를 여러 문서에서 맞춰야 했고, 최종 검증이 낡은 문구 하나를 찾았습니다. 이 안내서는 수치를 레지스트리 한 곳에 두어 이 문제를 구조로 막습니다.

회귀검증이 스스로 속는 경우(빈 출력끼리 비교, 비교 범위보다 넓은 주장, 비결정성, 의미가 다른 대체 구현, 측정 잡음)와 그것을 막는 도구는 회귀 고정에 따로 정리했습니다.

하지 말 것

"다시 확인해 줘"같은 맥락의 자기 검토는 같은 맹점으로 같은 결론에 이릅니다.
결론을 적어 보내는 검증 요청"이게 맞는지 봐 줘"는 동의를 부릅니다. 산출물과 범위만 주고 반증을 요청합니다.
원본에서 실험검증이 원본을 바꾸거나, 공유한 빌드 결과로 거짓 통과·거짓 실패가 납니다.
권한 있는 곳에서 검증공격하라고 시킨 에이전트는 실제로 공격합니다. 비밀값·푸시 권한이 없는 사본이나 샌드박스에서 돌립니다.
범위 없는 "통과"무엇을 어디서 봤는지 없는 통과는 확인이 아닙니다.
발견을 검증 없이 반영검증자도 틀립니다. 재현하고 채택합니다.
테스트를 고쳐서 통과회귀 테스트가 실패하면 기준이 아니라 코드를 의심합니다.
