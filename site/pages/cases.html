공개 레포 적용 사례

결론

Rust 코드를 쓰는 것이 첫 단계인 후보는 없었습니다 추론. 원인을 재 보면 반복 파싱, 매번 다시 짓는 색인, 화면 스레드에서 도는 계산처럼 언어와 무관한 문제가 먼저 나옵니다. 첫 단계에서 쓴 Rust는 orjson, ruff, oxlint, uv처럼 이미 만들어진 도구였습니다. Rust 코드는 그것을 고친 뒤에도 남는 비용에 씁니다. 결론의 등급이 추론인 것은 전제 일부(Web Worker의 효과, work-atlas의 다음 단계)가 아직 추론이기 때문입니다.

모든 전후 비교는 ⑦ 회귀 고정의 방식으로 했고, 아래 수치 가운데 등급이 확인인 것은 2026-11-01에 저장된 절차로 다시 잰 원자료가 있습니다. 그 과정에서 비교 자체가 속은 경우가 ⑦의 출발점이 됐습니다(회귀 고정). 이력과 재현 자료: {{doc:reports/2026-10-30-hotspots.md}}

work-atlas — Claude Code 훅 지연

원인

훅은 편집·프롬프트마다 새 Python 프로세스로 돕니다. 질의 계산 자체는 수 ms이고 시간은 매 호출의 준비 작업에 갑니다. 역할 설정이 비어 있어도 코드북 YAML을 순수 Python으로 파싱하고, 훅이 쓰지 않는 jsonschema를 import하고, 텍스트 색인을 질의마다 두 번 다시 짓습니다 기록됨.

1단계 · Python 그대로

3개 파일 30줄 패치(색인 한 번만 짓기, 지연 import, YAML C 로더, Rust로 구현된 orjson)로, 원본과 패치를 번갈아 21회 잰 중앙값이 편집 훅 {{fig:wa.edit}}, 프롬프트 훅 {{fig:wa.prompt}} 줄었습니다(LANG·ZK, 두 번 측정). 같은 원본끼리 잰 A/A는 {{fig:wa.aa}}였으니 잡음 바닥보다 훨씬 큰 변화입니다. 앞선 날의 측정도 편집 {{fig:wa.history.edit}}, 프롬프트 {{fig:wa.history.prompt}}로 같은 범위였습니다. 반면 같은 명령의 절대 중앙값은 날마다 {{fig:wa.abs}}로 달랐습니다.

회귀 고정: 훅 출력 4종이 바이트 단위로 같고 두 번째 실행에서도 같았습니다. 같은 기준 시각으로 지은 모델 파일도 바이트 단위로 같았고, 테스트 {{fig:wa.tests}}는 orjson이 있을 때와 없을 때 모두 통과했습니다. 전체 빌드는 쌍마다 {{fig:wa.build}} 줄었는데, 훅과 달리 폭이 측정마다 크게 흔들렸습니다. orjson이 거부하는 입력은 표준 json으로 다시 읽게 해 경계 입력의 결과·오류가 원본과 같습니다. 남는 차이(64비트를 넘는 정수를 float로 읽음)는 패치 설명에 적었습니다. work-atlas 규칙(엔진 변경은 사람 합의)에 따라 PR #1로 올렸습니다.

2단계 · Rust

유사도 질의를 Rust로 옮긴 프로토타입은 같은 색인 파일에서 Python과 {{fig:sim.same}} 결과가 같았고(앞선 날에는 합성 다국어 질의와 반올림 경계 값 색인에서도 {{grade:C-sim-same-old}}), 질의 1회를 프로세스 단위로 {{fig:sim.proc}}에 처리했습니다. 다만 이 차이의 대부분({{fig:sim.startup}})은 Python 기동과 import입니다. 같은 프로세스 안의 색인 읽기와 질의만 비교하면 {{fig:sim.inproc}}라서, PyO3로 훅에 붙이면 이득이 작습니다 추론. 규모와 무관하게 빠르려면 build 때 질의용 색인을 저장하는 형식 변경이 먼저입니다 추론.

판단

1단계는 지금 적용할 가치가 있습니다. Rust는 데이터가 ZK의 수 배를 넘어 프롬프트 훅이 1초에 다가갈 때, 독립 실행 파일로 꺼낼 카드입니다 추론.

docbench — 문서 비교가 화면을 멈춘다

원인

4,334줄 문서에서 가벼운 수정은 {{fig:db.js.light}}지만, 크게 다시 쓴 판은 {{fig:db.js}}가 걸렸고 이 계산이 화면 스레드에서 돕니다. 시간은 줄 단위 Myers diff와, 바뀐 줄마다 도는 낱말 diff에 나뉩니다. jsdiff의 낱말 토크나이저는 한글을 단어 문자로 보지 않아 한글을 글자 하나씩 토큰으로 쪼갭니다 기록됨. 그래서 한글 문서에서 특히 무겁습니다.

1단계 · JavaScript 그대로

diff를 Web Worker로 옮기면 계산이 길어도 화면은 멈추지 않습니다 추론. jsdiff의 timeout(200)·maxEditLength(1000) 옵션은 각각 {{fig:db.caps}} 만에 포기하고 undefined를 돌려주므로 "변경이 많아 전체 비교로 보기" 같은 대체 화면이 함께 필요합니다.

2단계 · Rust → WASM

같은 의미(같은 토크나이저, 휴리스틱 없는 Myers)로 옮겨 V8에서 JSON 왕복까지 포함해 재면 {{fig:db.wasm}}입니다. 더한·지운 줄 수는 {{fig:db.counts}} jsdiff와 같았고, 줄 목록은 {{fig:db.lines}}에서 같았지만, 낱말 강조까지 같은 것은 {{fig:db.highlight}}였습니다. 나머지는 크기가 같은 다른 최소 diff라 강조 위치가 다를 수 있습니다. 무작위 입력 4,000쌍에서는 {{fig:db.fuzz}}가 같았습니다. 작은 수정에서는 복사 비용 때문에 오히려 느리고({{fig:db.wasm.small}}), wasm 파일은 최적화 전 {{fig:db.wasm.size}}입니다. 작업량이 방향을 뒤집는 예입니다.

판단

Worker를 먼저 적용합니다. 화면 멈춤은 그것만으로 사라집니다. WASM은 큰 한글 문서 비교가 실제로 자주 일어날 때 일정 크기 이상에만 쓰는 조건부 경로입니다 추론.

Rust 코드 0줄로 Rust 도구 들이기

ruff는 work-atlas 16,738줄을 {{fig:tool.ruff}}, oxlint는 docbench 약 2만 1천 줄을 {{fig:tool.oxlint}}에 검사합니다. 두 레포 모두 CI에 린트 단계가 없습니다. 발견은 ruff {{fig:tool.ruff.n}}, oxlint {{fig:tool.oxlint.n}}이었고, 확인한 범위에서는 위험 패턴과 죽은 코드였을 뿐 확인된 버그는 없었습니다 추론. 설치 도구 uv는 work-atlas 가상환경 설치를 {{fig:tool.uv}}로 줄였습니다(각 1회).

가치는 속도보다, AI가 쓴 코드에 항상 걸리는 빠른 게이트라는 데 있습니다 추론. 게이트로 쓸 때는 절대 건수가 아니라 기준선 대비 새 경고로 봅니다. 도입 설정: {{doc:reports/2026-10-30-hotspots/tooling/README.md}}
