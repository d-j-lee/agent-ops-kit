# ⑦ 회귀 고정

| 항목 | 내용 |
|---|---|
| 실행 스킬 | `.claude/skills/aok-regress` (`/aok-regress`) |
| 스크립트 | `scripts/diffcheck.py`(차분 비교), `scripts/vacuity_check.py`(공허한 테스트 검사) |
| 계약 | 결과 주장은 `schemas/claim.schema.json`. [확인]의 `ref`는 다시 돌릴 수 있는 명령이다 |
| 기록 | PR 코멘트. 원장에는 아직 넣지 않는다(D25. 원장 `verifications.level`은 L·V 수준만 받는다) |
| 상태 | v1 기능(D25, `docs/proposals/regression-harness-hub.md`) |

①은 판단이 필요한 주장을 독립된 눈으로 본다. ⑦은 판단이 필요 없는 비교, 즉 **바꾸기 전에 성립하던 것이 바꾼 뒤에도 성립하는지**를 기준과 반복으로 고정한다. 판단이 필요 없다고 해서 쉬운 것은 아니다. 비교 스크립트도 스스로 속는다(§4).

## 1. 쓸 때 / 안 쓸 때

| 쓸 때 | 안 쓸 때 |
|---|---|
| 버그 수정, 리팩터링, 언어 이식, 성능 최적화, 라이브러리 교체 | 기준이 없는 새 기능의 정답 판정(①이나 사람) |
| ④ 루프의 라운드마다(수정이 회귀를 만든다) | 판단·해석이 필요한 주장(①) |
| 수치·개수를 고친 문서(같은 수치가 나오는 다른 곳) | 깨끗한 환경에서의 재현 자체(③) |

## 2. ①·③·④와의 관계

| 질문 | 기능 | 판정 방식 |
|---|---|---|
| 다른 눈으로 봐도 같은가 | ① L1 블라인드 + 판정자 | 독립 판단, 기계 대조 |
| 어떻게 하면 깨지는가 | ① L0, L1 반례 렌즈, ④ reviewer | 실험으로 재현한 것만 채택(S8) |
| 깨끗한 곳에서 문서대로 되는가 | ③ | 글자 그대로 실행 |
| **고친 뒤에도 전에 되던 것이 되는가** | **⑦** | 고정된 기준 + 대조군 + 자동 반복 |

④의 reviewer가 "고쳤다"를 보고, ⑦은 "깨지지 않았다"를 본다. 둘은 서로를 대신하지 않는다.

①과는 나눠 맡는다. 비교 자체(같은가, 실패하는가)는 ⑦이 기계로 한다. 그 비교가 무엇을 증명하는지(투영이 주장만큼 넓은가, 시나리오가 대표적인가)는 판단이므로 ①이 본다. T2 PR이면 ⑦의 결과를 ① L0 packet에 넣는다.

## 3. 절차 (런북)

1. **기준을 고정한다.**
   - 비교 전에 비결정성을 없앤다. 시각(`--as-of` 같은 옵션), 난수 시드, 세션·캐시 상태, 로캘·시간대, 실행하는 컨테이너(원격 자식마다 다르다)가 대상이다.
   - 상태를 기억하는 도구에는 실행마다 새 키를 준다(`diffcheck.py`의 `{nonce}`). 키 자체로 갈래가 나뉘는 도구(키를 해시해 보류군을 고르는 등)면 `--same-nonce`로 한 쌍의 양쪽에 같은 새 키를 준다. 이때 `--determinism`의 두 번째 실행은 새 키를 받으므로 그 갈래가 달라 보일 수 있다. 갈래를 정규화하거나 결정성은 고정 키로 따로 본다(보고에 note가 남는다).
   - 기준 커밋 sha를 기록한다. 기준이 없으면(빈 저장소, 얕은 클론, 지워진 base) 통과가 아니라 비교 불가로 멈춘다.
   - 양쪽이 상태를 공유하지 않게 한다. 빌드 디렉터리·캐시·출력 경로는 쪽마다 따로 둔다.
2. **실패 테스트 먼저(FAIL_TO_PASS).** 버그 수정이면 그 버그를 재현하는 테스트를 먼저 만들어 실패 출력을 보존하고, 고친 뒤 통과를 본다.
3. **전체 테스트(PASS_TO_PASS).** 고친 파일의 테스트만이 아니라 전부 돌린다. 선택 의존성·기능 플래그·OS가 갈리면 갈래마다 돌린다. CI는 대개 한쪽 경로만 탄다.
4. **음성 대조: 테스트가 공허하지 않은가.** 새 테스트와 보호 장치마다, 보호하려는 코드를 바꾼 변형에서 그 테스트가 실패하는지 본다.
   ```
   python3 -I scripts/vacuity_check.py --repo . --test "$TEST_CMD" --mutations muts.json [--jobs 4]
   ```
   - 변이는 테스트가 아니라 대상 코드에 넣고, 문법이 유효해야 한다. `.py` 변이가 컴파일되지 않으면 `invalid`로 거부된다.
   - 변이마다 `expect`에 그 변이를 잡아야 할 테스트 이름을 적는다(낱말 단위로 맞춘다). 다른 이유로 실패하면 `other_failure`이고 통과가 아니다. 한계: `expect`가 없으면 어떤 실패든 `guarded`다. 실행 중에 죽는 변이는 지정한 테스트도 오류로 만들어 `guarded`로 셀 수 있고, `-v`처럼 통과한 테스트 이름도 출력하는 실행에서는 이름이 맞아 버린다. 테스트 파일 자체를 바꾼 변이는 테스트를 망가뜨려 실패할 뿐이라 보호 장치의 증거가 아니다. 변이는 보호 코드에, 실행되는 형태로 두고, 테스트 명령은 실패한 것만 이름을 내는 형태로 쓴다.
   - 변이는 정확히 한 곳에 맞아야 한다. 통과해 버리는 변이(`vacuous`)가 있으면 그 테스트는 그 장치를 지키지 않는다. 시간 초과는 `timeout`(판정 보류)이다.
5. **차분 비교와 양성 대조(A/A).** 같은 입력을 기준과 후보에 넣는다.
   ```
   python3 -I scripts/diffcheck.py --base "$BASE_CMD" --cand "$CAND_CMD" [--stdin input.json] \
     [--normalize "$VOLATILE_REGEX"] [--stderr] --determinism [--timing 21] --json
   ```
   - 빈 출력(공백뿐이거나 정규화 뒤 `<N>`만 남은 것 포함), 0이 아닌 종료 코드, 시간 초과는 실패다. 비어 있어도 되는 경우만 `--allow-empty`를 쓴다.
   - `--allow-fail`은 0이 아닌 종료를 그 자체로 실패로 보지 않을 뿐이다. 종료 코드는 계속 비교한다.
   - 출력은 바이트로 비교한다(줄 끝 변환·디코딩 손실 없음). 기본 비교 대상은 종료 코드와 stdout이고, 보고의 `compared`에 남는다. stderr에 의미가 있으면(훅의 차단 메시지 등) `--stderr`를 준다.
   - `--determinism`은 각 쪽을 두 번 돌려 종료 코드·출력이 같은지 본다. 이것이 A/A 대조다. 다르면 비교 결과를 믿을 수 없다.
   - 정규화는 무엇을 몇 번 바꿨는지 보고에 남고, 양쪽 횟수가 다르면 `differs`다. 모두 지우는 정규식으로 "같다"를 만들 수 없다(빈 출력으로 실패, `--stderr`면 stderr도). "아무 일 없음"을 `{}` 같은 고정값으로 내는 도구는 그 값을 정규화로 지우면 빈 출력 검사가 잡는다.
   - 무엇을 비교했는지(투영)를 보고에 적는다. 줄 목록만 비교했다면 "화면이 같다"고 쓰지 않는다.
   - 손으로 고른 사례에 더해 무작위 입력을 넣는다. 고른 사례는 고른 사람의 맹점을 공유한다.
   - 한 번은 알려진 차이를 넣은 후보로 돌려 `differs`가 나는지 본다. 비교가 아무것도 못 잡는 설정(투영이 너무 좁음, 정규화 과다)을 거른다.
6. **성능.**
   - `--timing N`은 기준과 후보를 번갈아 돌린다. 한쪽을 몰아서 돌리면 시간에 따른 잡음이 한쪽에만 들어간다.
   - 먼저 기준끼리(`--base X --cand X`) 재서 잡음 바닥을 안다. 변화가 잡음 바닥보다 작으면 효과로 쓰지 않는다.
   - 보고에는 한 번의 측정이 아니라 측정 간 범위를 쓴다. 절대값은 그 머신에서만 성립하고, 비율을 본다.
   - 측정 경계를 배포 형태에 맞춘다(프로세스 단위인지 프로세스 안인지). 작업량이 방향을 뒤집을 수 있으니 작은 경우와 큰 경우를 함께 잰다.
   - 성능 수치의 재현은 같은 값이 아니라 잡음 바닥·범위 안에 드는지로 판정한다.
7. **대체 구현.** 더 빠른 라이브러리나 다른 언어로 바꿀 때는 경계 입력표를 만들어 원본과 대조한다. 예: JSON이면 NaN·Infinity·아주 큰 수·짝 없는 서로게이트·깊은 중첩·잘못된 인코딩·BOM. 수치 이식이면 반올림 방식과 실수 파싱(1 ULP), 그리고 일부러 만든 경계 값.
8. **린트·경고 수.** 절대 건수를 게이트로 쓰지 않는다. 기준선과 비교한 "새 경고 0"으로 본다.
9. **문서 수치.** 수치나 개수를 바꾸면 그 값이 나오는 모든 곳을 함께 고친다(`grep`). 읽기 허브는 수치 레지스트리와 빌드 검사가 이것을 구조로 막는다(`site/claims.json`, D28). 일관성 검사는 정확성 검사가 아니다. 모든 사본이 같이 틀릴 수 있다.
10. **기록.** PR 코멘트에 `diffcheck --json`과 `vacuity_check --json`의 요약을 남긴다. 주장은 claim 형식으로, [확인]의 `ref`는 위 명령 그대로 쓴다. 측정 환경(머신, 버전, 날짜)을 `scope`에 적는다. 공개 레포에는 판정·수치·해시만 남기고, 대상의 출력 원문은 대상 레포 CI 산출물이나 원장 포인터로 둔다.

## 4. 실패 모드와 대응

| 실패 | 사례 | 대응 |
|---|---|---|
| 빈 출력끼리 "같다" | 세션 ID를 재사용해 훅이 두 번째부터 아무것도 내지 않았다 [기록됨] | `diffcheck`가 빈 출력을 실패로 본다. 실행마다 `{nonce}` |
| 비교 범위보다 넓은 주장 | 줄 목록만 비교하고 "화면이 같다". 낱말 강조까지 같은 것은 9개 중 3개 [기록됨] | 투영을 보고에 적는다. 무작위 입력 |
| 비결정성 | 기준 시각 없이 빌드하면 매번 다른 `categories.json` [기록됨] | 시각·시드·상태 고정, `--determinism` |
| 의미가 다른 대체 구현 | orjson이 NaN·큰 수에서 표준 `json`과 다르게 동작. 기존 테스트는 다 통과 [기록됨] | 경계 입력표로 대조 |
| 공허한 테스트 | 보호 장치를 지워도 통과하는 회귀 테스트 4개 [기록됨]. 이 키트의 ⑦ 도구 시험도 처음에는 문서에 적은 장치 다수를 지키지 못했다 [기록됨] | `vacuity_check`, 변이마다 `expect` |
| 깨진 변이를 "잡았다"로 | 문법 오류를 넣은 변이에서 무엇도 지키지 않는 테스트가 실패해 guarded로 나왔다 [기록됨] | `invalid`·`timeout`·`other_failure`는 통과가 아니다 |
| 측정 잡음 | 같은 훅 비교의 단축률이 실행마다 몇 %p씩 흔들린다. 절대값은 머신 부하에 따라 더 크게 움직인다 [기록됨] | 번갈아 측정, A/A 잡음 바닥, 범위 보고 |
| 공유 상태 | 시험 사본과 원본이 빌드 디렉터리를 공유해 원본 검증이 사본 산출물을 재사용했다 [기록됨] | 쪽마다 빌드·캐시 경로를 따로 |
| 기준이 없는 상태 | 빈 저장소의 첫 커밋에서 게이트가 비교 기준을 못 찾고 통과했다 [기록됨] | 기준이 없으면 비교 불가로 멈춘다 |
| 수치 이식 경계 | Rust 이식이 반올림 경계 값에서 Python과 달랐다(실수 파싱 1 ULP) [기록됨] | 일부러 만든 경계 값, 정확한 파싱 |
| 실패를 "결과 없음"으로 오해 | 잘못된 경로를 주자 비교 도구가 "찾은 것 없음"으로 보고 [기록됨] | 도구 실패는 판정이 아니다. 두 스크립트 모두 실행할 수 없으면 종료 코드 2로 멈춘다 |

사례는 출발점 세션의 기록이다. 이력과 재현 절차: `reports/2026-10-30-hotspots.md`(다시 잰 값은 그 폴더의 `logs/`), `reports/2026-10-30-verification-rounds.md`.
