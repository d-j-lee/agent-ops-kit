# ⑦ 회귀 고정

| 항목 | 내용 |
|---|---|
| 실행 스킬 | `.claude/skills/aok-regress` (`/aok-regress`) |
| 스크립트 | `scripts/diffcheck.py`(차분 비교), `scripts/vacuity_check.py`(공허한 테스트 검사) |
| 계약 | 결과 주장은 `schemas/claim.schema.json`. [확인]의 `ref`는 다시 돌릴 수 있는 명령이다 |
| 기록 | PR 코멘트. 원장에는 아직 넣지 않는다(D19, `docs/proposals/regression-harness-hub.md`) |
| 상태 | 제안 단계(D19). 채택되면 v1 기능 |

①은 판단이 필요한 주장을 독립된 눈으로 본다. ⑦은 판단이 필요 없는 비교, 즉 **바꾸기 전에 성립하던 것이 바꾼 뒤에도 성립하는지**를 기준과 반복으로 고정한다. 판단이 필요 없다고 해서 쉬운 것은 아니다. 비교 스크립트도 스스로 속는다(§4).

## 1. 쓸 때 / 안 쓸 때

| 쓸 때 | 안 쓸 때 |
|---|---|
| 버그 수정, 리팩터링, 언어 이식, 성능 최적화, 라이브러리 교체 | 기준이 없는 새 기능의 정답 판정(①이나 사람) |
| ④ 루프의 라운드마다(수정이 회귀를 만든다) | 판단·해석이 필요한 주장(①) |
| 수치·개수를 고친 문서(같은 수치가 나오는 다른 곳) | 깨끗한 환경에서의 재현 자체(③) |

## 2. ①·③·④와의 관계

| 질문 | 기능 | 판정 방식 |
|---|---|---|
| 다른 눈으로 봐도 같은가 | ① L1 블라인드 + 판정자 | 독립 판단, 기계 대조 |
| 어떻게 하면 깨지는가 | ① L0, L1 반례 렌즈, ④ reviewer | 실험으로 재현한 것만 채택(S8) |
| 깨끗한 곳에서 문서대로 되는가 | ③ | 글자 그대로 실행 |
| **고친 뒤에도 전에 되던 것이 되는가** | **⑦** | 고정된 기준 + 자동 반복 + 공허함 방지 |

④의 reviewer가 "고쳤다"를 보고, ⑦은 "깨지지 않았다"를 본다. 둘은 서로를 대신하지 않는다.

## 3. 절차 (런북)

1. **기준을 고정한다.** 비교 전에 비결정성을 없앤다. 시각(`--as-of` 같은 옵션), 난수 시드, 세션·캐시 상태가 대상이다. 상태를 기억하는 도구에는 실행마다 새 키를 준다(`diffcheck.py`의 `{nonce}`). 기준 커밋 sha를 기록한다.
2. **실패 테스트 먼저(FAIL_TO_PASS).** 버그 수정이면 그 버그를 재현하는 테스트를 먼저 만들어 실패 출력을 보존하고, 고친 뒤 통과를 본다.
3. **전체 테스트(PASS_TO_PASS).** 고친 파일의 테스트만이 아니라 전부 돌린다. 선택 의존성이 있으면 있을 때와 없을 때 둘 다 돌린다. CI는 대개 한쪽 경로만 탄다.
4. **공허함을 검사한다.** 새 테스트와 보호 장치마다, 보호하려는 코드를 바꾼 변형에서 테스트가 실패하는지 본다.
   ```
   python3 -I scripts/vacuity_check.py --repo . --test "<테스트 명령>" --mutations <변이 목록.json>
   ```
   변이는 정확히 한 곳에 맞아야 한다. 통과해 버리는 변이(`vacuous`)가 있으면 그 테스트는 아무것도 지키지 않는다.
5. **차분 비교.** 같은 입력을 기준과 후보에 넣는다.
   ```
   python3 -I scripts/diffcheck.py --base "<기준 명령>" --cand "<후보 명령>" [--stdin 입력] \
     [--normalize '<비결정 부분 정규식>'] --determinism [--timing 21] --json
   ```
   - 빈 출력, 0이 아닌 종료 코드, 실행마다 다른 출력은 실패다. 비어 있어도 되는 경우만 `--allow-empty`를 쓴다.
   - 정규화는 무엇을 몇 번 바꿨는지 보고에 남는다. 모두 지우는 정규식으로 "같다"를 만들지 않는다.
   - 무엇을 비교했는지(투영)를 보고에 적는다. 줄 목록만 비교했다면 "화면이 같다"고 쓰지 않는다.
   - 손으로 고른 사례에 더해 무작위 입력을 넣는다. 고른 사례는 고른 사람의 맹점을 공유한다.
6. **성능.** `--timing N`은 기준과 후보를 번갈아 돌린다. 한쪽을 몰아서 돌리면 시간에 따른 잡음이 한쪽에만 들어간다. 보고에는 한 번의 측정이 아니라 측정 간 범위를 쓴다.
7. **대체 구현.** 더 빠른 라이브러리나 다른 언어로 바꿀 때는 경계 입력표를 만들어 원본과 대조한다. 예: JSON이면 NaN·Infinity·아주 큰 수·짝 없는 서로게이트·깊은 중첩·잘못된 인코딩·BOM. 수치 이식이면 반올림 방식과 실수 파싱(1 ULP), 그리고 일부러 만든 경계 값.
8. **문서 수치.** 수치나 개수를 바꾸면 그 값이 나오는 모든 곳을 함께 고친다(`grep`). 읽기 허브는 수치 레지스트리가 이것을 구조로 막는다(`site/claims.json`).
9. **기록.** PR 코멘트에 `diffcheck --json`과 `vacuity_check --json`의 요약을 남긴다. 주장은 claim 형식으로, [확인]의 `ref`는 위 명령 그대로 쓴다. 측정 환경(머신, 버전, 날짜)을 `scope`에 적는다.

## 4. 실패 모드와 대응

| 실패 | 사례 | 대응 |
|---|---|---|
| 빈 출력끼리 "같다" | 세션 ID를 재사용해 훅이 두 번째부터 아무것도 내지 않았다 [확인] | `diffcheck`가 빈 출력을 실패로 본다. 실행마다 `{nonce}` |
| 비교 범위보다 넓은 주장 | 줄 목록만 비교하고 "화면이 같다". 낱말 강조까지 같은 것은 9개 중 3개 [확인] | 투영을 보고에 적는다. 무작위 입력 |
| 비결정성 | 기준 시각 없이 빌드하면 매번 다른 `categories.json` [확인] | 시각·시드·상태 고정, `--determinism` |
| 의미가 다른 대체 구현 | orjson이 NaN·큰 수에서 표준 `json`과 다르게 동작. 기존 테스트는 다 통과 [기록됨] | 경계 입력표로 대조 |
| 공허한 테스트 | 보호 장치를 지워도 통과하는 회귀 테스트 4개 [기록됨] | `vacuity_check` |
| 측정 잡음 | 몰아서 잰 비율이 측정마다 -32%~-50% [확인] | 번갈아 측정, 범위 보고 |
| 수치 이식 경계 | Rust 이식이 반올림 경계 값 13,048개 중 1,159개에서 Python과 달랐다(실수 파싱 1 ULP) [확인] | 일부러 만든 경계 값, 정확한 파싱 |
| 실패를 "결과 없음"으로 오해 | 잘못된 경로를 주자 비교 도구가 "찾은 것 없음"으로 보고 [기록됨] | 도구 실패는 실패로 멈춘다(두 스크립트 모두 종료 코드 2) |

사례의 이력: `reports/2026-10-30-hotspots.md`, `reports/2026-10-30-verification-rounds.md`.
