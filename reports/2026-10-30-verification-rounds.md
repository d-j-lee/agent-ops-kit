# 독립 검증 라운드 기록 — Rust 작업 하네스와 검증 플레이북 (2026-10-28~30)

> **이력 기록.** 규범 문서가 아니다. 한 세션에서 같은 산출물에 검증 방식을 바꿔 가며 붙인 결과다. ⑦ 회귀 고정(`docs/patterns/regression.md`, D25)과 ⑧ 작업 레포 하네스(D26) 제안의 근거다. 수치는 각 검증 서브에이전트의 보고서에 적힌 건수와 작업 완료 알림에 찍힌 시간·토큰이다. 둘 다 다시 돌릴 수 없는 기록이라 [기록됨]이다. 보고서 원문과 개별 발견의 공격 형태는 싣지 않는다(공개 레포 규칙, 아직 고쳐지지 않은 것이 있을 수 있다).

## 1. 대상

| 산출물 | 내용 |
|---|---|
| Rust 작업 하네스 | 에이전트 규칙, 단일 검증 진입점 `verify.sh`(policy·light·static·fast·full), Claude Code 훅 4개(세션 시작·프롬프트 기준점·편집 직후 검사·턴 종료 게이트), 적대적 리뷰어 서브에이전트, CI·Dependabot·cargo-deny, 예제 크레이트와 PyO3 브리지 |
| 검증 플레이북 | 교차·적대·회귀 검증의 차이, AI에서 달라지는 점(연구 근거), 라운드 설계, 브리핑 템플릿 |
| 공개 레포 핫스팟 | `reports/2026-10-30-hotspots.md` |

## 2. 라운드

| 단계 | 검증자 | 방식 | 찾은 것 | 시간 · 토큰 |
|---|---|---|---|---|
| 0 자기 검증 | 작성자 | 전체 게이트, 훅 시나리오 7개, shellcheck | "전달 가능"으로 판단 | — |
| 1 적대적 | 새 서브에이전트. 코드와 공격 범위만 받음(작성자 결론 없음) | 레포 사본에서 공격 실험 | 높음 4 · 중간 10 · 낮음 14 | 115.6분 · 195,845 |
| 2 회귀 재검증 | 1과 같은 서브에이전트(발견 목록 보유) | 발견마다 같은 실험을 다시 + 수정이 만든 회귀 탐색 | 높음·중간 중 FIXED 9 · PARTIAL 4. 새 문제 중간 2 · 낮음 2. 공허한 테스트 3 | 54.4분 · 261,878 |
| 3 적대적 | 새 서브에이전트. 앞 라운드 발견 목록은 받지 않음 | 최신 변경에 집중, 시간 제한 요청 | 높음 0 · 중간 3 · 낮음 5 · 문서 6. 공허한 테스트 1개 더 | 176.6분 · 206,517 |
| 팩트체크 | 새 서브에이전트 | 가이드의 주장을 출처와 대조, 과장 탐지 | 높음 3 · 중간 7 | 53.1분 · 219,749 |
| 4 적대적 | 새 서브에이전트 | 플레이북 + 핫스팟 결과물 | 높음 0 · 중간 6 · 낮음 다수 | 약 33분 |
| 5 회귀 재검증 | 4와 같은 서브에이전트 | 수정 확인 | 중간 6 모두 FIXED. 새 높음·중간 0. 낮음 8 → 모두 고침 | 약 10분 |

시간·토큰은 작업 완료 알림 기준이다. 토큰은 알림에 표시된 값이고, 누적 사용량인지 마지막 맥락 크기인지는 [미확인]이다. 4·5의 시간은 서브에이전트 기록의 첫·마지막 시각 차이라 정의가 다르다. 라운드끼리 시간을 비교하지 않는다.

1라운드의 높음·중간 14건(4 + 10) 가운데 2라운드 판정이 남은 것은 13건(FIXED 9, PARTIAL 4)이다. 나머지 1건의 판정은 남은 기록에서 찾지 못했다 [미확인].

## 3. 관찰

| 관찰 | 내용 | 등급 |
|---|---|---|
| 자기 검증은 "완료"라고 했다 | 게이트와 시나리오 테스트를 통과한 뒤에도 분리된 적대적 검증이 높음 4건을 찾았다. 네 건 모두 작성자가 미리 적어 둔 시나리오 목록에 없던 경로였다 | [기록됨] |
| 수정은 회귀를 만든다 | 2라운드와 3라운드 모두 직전 수정이 만든 회귀를 찾았다(예: 2라운드 수정 뒤 빈 저장소의 첫 커밋으로 게이트가 우회됨) | [기록됨] |
| 회귀 테스트도 검증해야 한다 | 수정마다 만든 회귀 테스트 중 4개가 보호 장치를 지워도 통과했다 | [기록됨] |
| 검증 환경도 속인다 | 테스트용 사본과 원본이 빌드 디렉터리를 공유하자 원본 검증이 사본에서 빌드된 산출물과 경고를 재사용했다. 2라운드에서 거짓 실패가 재현됐다 | [기록됨] |
| 같은 검증자와 새 검증자는 역할이 다르다 | 같은 검증자는 발견 목록을 들고 있어 수정 확인이 빨랐다. 새 검증자는 앞 라운드가 보지 못한 회귀를 찾았다 | [기록됨], 해석은 [추론] |
| 새로 찾은 높음은 빠르게 줄었다 | 새 발견 높음 4 → 0 → 0, 중간 10 → 2 → 3. 2라운드에는 부분 수정 4건(높음 1 · 중간 3)이 남아 있었다 | [기록됨] |
| 시간 제한은 프롬프트로 지켜지지 않는다 | 3라운드에 "한 시간 안쪽"을 요청했으나 176.6분이 걸렸다 | [기록됨] |
| 공격하라고 하면 실제로 공격한다 | 1라운드 검증자는 권한 규칙의 빈틈으로 임의 명령을 실행할 수 있음을 실험으로 보였다. 검증자는 비밀값과 푸시 권한이 없는 사본에서 돌려야 한다 | [기록됨] |
| 멈춤 기준을 다 지키지 못했다 | 3라운드의 중간 3건은 고친 뒤 실패 → 통과 테스트로 확인했지만 새 검증 라운드는 돌리지 않았다. 5라운드 뒤에도 새 검증자 라운드는 돌리지 않았다. ④의 종료 조건으로 보면 사람이 남은 위험을 받아들일지 정해야 하는 경우다. 6라운드(§5)가 그 빈자리를 메운 첫 새 검증자 라운드다 | [기록됨] |

## 5. 이 키트의 PR #4에 붙인 ① T2 (2026-10-31~11-01)

⑦과 읽기 허브를 키트에 넣는 PR 자체를 `aok-verify` T2로 검증했다. 출발점 세션의 라운드 번호를 이어 6라운드로 부른다.

| 항목 | 내용 |
|---|---|
| 구성 | L1 두 렌즈(주장별 판정, 블라인드 재설계): 질문·원자료·재현 절차만 받음. L0 두 렌즈(주장 검토, 반례 탐색): PR 전체를 받음. 판정자: 별도 서브에이전트. L2는 원격 자식 생성 도구가 없어 돌리지 못했다 |
| 무결성 | 카나리 누출 0(패킷 검사 종료 0, 출력 검사 일치 0). 무효 출력 0 |
| 결과 | 작성자 주장 15건 중 일치 9 · 반박 4 · 미검증 2. 검증자만 찾은 항목 44건(중복을 묶은 수). 검증자가 실행하지 못한 항목 51건은 통과로 세지 않았다 |
| 확정 오류 | 2건. 허브 빌드의 검사 목록이 실제 검사보다 넓었다(없는 파일 링크·손으로 단 [확인]·공유 링크 형식 URL이 통과). 허브 수치는 레지스트리에서만 온다는 결정이 빌드에 없었다 |
| 사람 판단으로 올라온 것 | 2건. diffcheck의 결정성 검사가 두 번째 실행의 종료 코드를 보지 않았고 시험이 번갈아 측정·정규화 횟수·입력 파일의 `{nonce}`를 지키지 못했다. vacuity_check가 절대 경로 심볼릭 링크를 따라가 원본을 고칠 수 있었다. 둘 다 주장을 좁히지 않고 도구를 고쳤다 |
| 등급 조정 | 작성자 원장의 [확인] 4건이 [추론]으로, 결론이 [추론]으로 내려갔다. 다시 돌릴 ref 없이 보고서 파일만 가리킨 [확인]이 주된 이유였다 |
| 작성자 쪽 과정 오류 | 질문 매핑(qmap)이 L1 질문 번호와 맞지 않아 판정자가 모든 연결을 뜻으로 했다. L0 검증자의 target 번호도 작성자 주장 id가 아니었다 |

**검증자만 찾은 것 중 주요 부류** (모두 R1에서 고쳤다. 기존 결함은 따로 표시)

| 부류 | 내용 |
|---|---|
| 비교기의 거짓 통과 | 다른 잘못된 바이트가 같은 대체 문자로 바뀌어 "같다", 공백뿐인 출력, 모두 지우는 정규화, `--allow-fail`에서 종료 코드 무시, 양쪽 시간 초과, stderr 무시 |
| 공허함 검사기의 거짓 통과 | 문법 오류·시간 초과·다른 이유의 실패를 "잡았다"로 셈 |
| 도구 실패와 판정의 혼동 | 실행 권한 없는 명령, 디렉터리가 아닌 작업 경로, UTF-8이 아닌 입력이 종료 1로 끝났다 |
| 허브의 수치·등급 | 본문에 직접 쓴 수치, 보고서 파일만 가리키는 [확인], 자리표시가 든 근거 명령, 범례가 규범의 등급 정의를 바꿈, 원자료 없는 터미널 발췌 |
| 문서 상태 | 병합하면 채택인데 문서는 계속 "제안", 결정 번호가 다른 문서와 겹침 |
| 공개 레포 위생 | 검증 기록에 개별 공격 형태 |
| 기존 결함 | 클린룸의 작업 트리 검사가 스테이징·커밋·새 파일을 놓침, BRD 비용의 [도출] 값, README의 커밋 전 스캔에 `--strict` 없음, 검증자 도구 설명 불일치, 결정적 비교와 위험 등급 규칙의 충돌 |

R1에서 함께 한 것: 원자료가 없던 핵심 수치를 2026-11-01에 저장한 절차로 다시 재서 `2026-10-30-hotspots/logs/`에 남겼다. 다시 잰 값은 절대값이 크게 달랐고(머신 상태) 훅의 단축 비율은 같은 범위였으며, 전체 빌드의 단축 폭은 처음 보고보다 작고 흔들렸다. 원자료를 남기지 못한 값은 [기록됨]으로 내렸다.
