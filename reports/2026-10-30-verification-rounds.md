# 독립 검증 라운드 기록 — Rust 작업 하네스와 검증 플레이북 (2026-10-28~30)

> **이력 기록.** 규범 문서가 아니다. 한 세션에서 같은 산출물에 검증 방식을 바꿔 가며 붙인 결과다. ⑦ 회귀 고정(`docs/patterns/regression.md`, D25)과 ⑧ 작업 레포 하네스(D26) 제안의 근거다. 수치는 각 검증 서브에이전트의 보고서에 적힌 건수와 작업 완료 알림에 찍힌 시간·토큰이다. 둘 다 다시 돌릴 수 없는 기록이라 [기록됨]이다. 보고서 원문과 개별 발견의 재현 절차는 싣지 않는다(공개 레포 규칙, 아직 고쳐지지 않은 것이 있을 수 있다). 발견은 부류(예: "비교 기준이 없는 상태에서 게이트가 통과")로만 적는다.

## 2. 라운드

| 단계 | 검증자 | 방식 | 찾은 것 | 시간 · 토큰 |
|---|---|---|---|---|
| 0 자기 검증 | 작성자 | 전체 게이트, 훅 시나리오 7개, shellcheck | "전달 가능"으로 판단 | — |
| 1 적대적 | 새 서브에이전트. 코드와 공격 범위만 받음(작성자 결론 없음) | 레포 사본에서 공격 실험 | 높음 4 · 중간 10 · 낮음 14 | 115.6분 · 195,845 |
| 2 회귀 재검증 | 1과 같은 서브에이전트(발견 목록 보유) | 발견마다 같은 실험을 다시 + 수정이 만든 회귀 탐색 | 높음·중간 중 FIXED 9 · PARTIAL 4. 새 문제 중간 2 · 낮음 2. 공허한 테스트 3 | 54.4분 · 261,878 |
| 3 적대적 | 새 서브에이전트. 앞 라운드 발견 목록은 받지 않음 | 최신 변경에 집중, 시간 제한 요청 | 높음 0 · 중간 3 · 낮음 5 · 문서 6. 공허한 테스트 1개 더 | 176.6분 · 206,517 |
| 팩트체크 | 새 서브에이전트 | 가이드의 주장을 출처와 대조, 과장 탐지 | 높음 3 · 중간 7 | 53.1분 · 219,749 |
| 4 적대적 | 새 서브에이전트 | 플레이북 + 핫스팟 결과물 | 높음 0 · 중간 6 · 낮음 다수 | 약 33분 |
| 5 회귀 재검증 | 4와 같은 서브에이전트 | 수정 확인 | 중간 6 모두 FIXED. 새 높음·중간 0. 낮음 8 → 모두 고침 | 약 10분 |

시간·토큰은 작업 완료 알림 기준이다. 토큰은 알림에 표시된 값이고, 누적 사용량인지 마지막 맥락 크기인지는 [미확인]이다. 4·5의 시간은 서브에이전트 기록의 첫·마지막 시각 차이라 정의가 다르다. 라운드끼리 시간을 비교하지 않는다.

1라운드의 높음·중간 14건(4 + 10) 가운데 2라운드 판정이 남은 것은 13건(FIXED 9, PARTIAL 4)이다. 나머지 1건의 판정은 남은 기록에서 찾지 못했다 [미확인].

### 5.1 R1 수정의 재검증 (7라운드, 11-01)

R1에서 고친 판(PR #4 e492e45)을 다시 T2로 검증했다. 이번에는 R1 지적이 고쳐졌는지와 고친 것이 새 구멍을 만들었는지가 질문이라, 결론을 담은 산출물을 주는 L0만 돌렸다 [추론: 질문의 성격에서 고른 구성].

| 항목 | 내용 |
|---|---|
| 구성 | L0 두 렌즈(R1 지적별 해소 판정, 반례 탐색). 판정자: 별도 서브에이전트. L1·L2는 돌리지 않았다 |
| 무결성 | 카나리 누출 0, 오염 0, 무효 출력 0 |
| 결과 | 작성자 주장 9건 중 일치 3 · 반박 5 · 미검증 1. 검증자만 찾은 항목 31건(그중 3건은 지지 확인). 검증자가 실행하지 못한 항목 53건은 통과로 세지 않았다 |

**R2에서 고친 부류**

| 부류 | 내용 |
|---|---|
| 비교기 | stderr까지 정규화로 비워지면 실패, 양쪽 정규화 횟수가 다르면 차이, 시간 측정의 실행마다 새 키, 측정 중 시간 초과는 실패, 키 고정과 결정성 검사를 함께 쓰면 보고에 주의, 유한하지 않은 시간 제한은 사용 오류 |

### 7.1 찾은 것의 부류

공개 레포라 개별 우회 형태는 싣지 않고 부류만 적는다. 재현은 판정자 작업 디렉터리의 원자료에 있다(레포 밖).

| 부류 | 무엇이 틀렸나 | 처리 |
|---|---|---|
| 게시 대상 | 게이트는 체크아웃한 트리를 보는데, 다른 ref나 옵션을 바꾼 형태의 게시가 그 트리와 상관없이 허용됐다 | 명령을 셸 단어로 나눠 게시 대상과 같은 명령 안의 HEAD 이동을 본다. 훅을 끄는 옵션은 묶음 형태와 따옴표까지 본다 |
| 판정 정의의 출처 | CI의 `--base`가 정의 파일만 기준 브랜치에서 읽고 어댑터·코어는 PR 것을 썼다. 기준 커밋에 정의가 없거나 세션 상태가 없으면 작업 트리 정의를 썼다 | 어댑터 사본도 기준 커밋에서 읽는다. 기준 커밋에 없는 정의는 쓰지 않는다. CI는 기준 브랜치에서 꺼낸 코어로 돈다(런북 §3) |
| 닫힌 실패의 구멍 | 상태 저장이 실패하면 출력 없이 종료 1(Claude Code는 진행시킨다), 위임한 fsmap의 패닉 코드를 그대로 넘김, 설치한 훅에 `onFailure`가 없음, 설정의 형이 틀리면 traceback | 어떤 경로에서도 block·deny JSON을 낸다. 위임은 0·2만 답으로 받는다. PreToolUse에 `onFailure: "block"`. 설정의 모양과 예산 상한을 검사해 실행 불가(2)로 |
| 귀속 | 빈 레포에서 그대로 첫 커밋한 파일, 상태 없이 이어받은 fork, 푸시 전 게이트가 먼저 통과한 턴의 약화 보고가 빠졌다. 기준 정의가 깨진 레포에서 아무것도 안 바꾼 세션이 막혔다 | 규칙을 고치고 각각 시험으로 고정했다 |
| 약화 탐지 | 파일 단위 억제, `expectedFailure`·`SkipTest`, 시험 이름 바꾸기, 빈 스위트, 시험 파일을 수집 경로 밖으로 옮기기를 보지 못했다. 단언을 강화해도 지운 것으로 셌다 | 규칙을 더하고 순수 감소로 센다. 정규식으로 못 잡는 형태는 한계로 적었다 |
| 보호 경로 | CI 워크플로와 설치된 리뷰어가 빠져 있었고, 무시된 로컬 설정은 보이지 않았다 | 보호 목록을 넓히고 무시된 파일도 해시로 본다. 설정 파일은 훅·환경 키만 본다(Claude Code가 스스로 쓰는 권한 규칙 때문) |
| install | 모양이 다른 설정에서 traceback, 이미 있는 정의와 다른 `--adapter`를 조용히 무시하고 계획은 다르게 보임, 인터프리터를 바꾸면 훅이 둘 | 쓰기 전에 거부(2)하고, 하네스 훅은 명령 모양이 아니라 코어 이름과 이벤트로 찾는다 |
| 문서 불일치 | 공식 문서에 있는 `background_tasks`와 Stop 연속 상한을 "없다·미확인"으로 적음, 막힘 횟수, 기준에 "작업 트리 지문"이 있다는 docstring, fsmap에 "모든 훅"을 넘긴다는 서술(prompt는 넘기지 않았음), 리뷰어 사본이 커밋 안 된 변경을 담지 않음 | [문서]로 바로잡고, prompt도 넘기며, 리뷰어는 작업 트리째 복사하고 원격을 지운다 |

| worktree | worktree에 들어가거나 `cd`해도 `CLAUDE_PROJECT_DIR`는 처음 자리에 남고 훅 입력의 `cwd`가 따라간다. 프로젝트·추가 디렉터리 밖으로 간 `cd`는 다음 명령에 이어지지 않는다 [문서] | 세션의 상태는 하나(프로젝트 디렉터리)다. 세션이 일한 같은 레포의 worktree(명령이 들어가거나 만든 곳, 편집한 곳, 턴이 끝나는 곳)를 턴이 어디서 끝나든 모두 판정하고, worktree의 HEAD는 세션 시작 때와 비교한다. 게시는 게시가 도는 트리에서 판정한다 |

worktree의 첫 설계(훅 입력의 `cwd`에 있는 worktree를, 그 worktree의 git 디렉터리에 따로 쌓은 상태로 판정)는 독립 검증자 하나(L0, 반례 탐색·주장별 판정·목록 밖 변이)가 반박했다. 설계를 바꿔 다시 짰다.

| 부류 | 찾은 것 | 고친 것 |
|---|---|---|
| 판정 범위 | 본 체크아웃으로 돌아오면 실패한 worktree를 둔 채 턴이 끝났다. 프로젝트 밖의 형제 worktree는 `cd`가 이어지지 않아 판정 대상이 되지 않았다 | 일한 worktree를 모두, 턴이 어디서 끝나든 판정한다. 명령 줄의 `cd`·`pushd`·`git -C`·`git worktree add`를 명령이 돌기 전에 읽는다 |
| 기준 | worktree를 처음 보기 전에 옮긴 HEAD(같은 명령 안의 병합·리셋)는 판정하지 않았다 | 세션 시작 때 worktree마다 HEAD를 적어 그것과 비교한다. 그 뒤에 만든 worktree는 시작 때의 ref와 비교한다 |
| 상태 | worktree의 상태 파일을 지우면 다시 이어받아 하네스 변경의 푸시 거부를 지났고, 실제 푸시가 나갔다. 막힘 횟수가 worktree마다였다 | 상태 하나, 막힘 횟수 하나. 하네스 파일을 바꾼 커밋은 턴 종료가 통과해도 통과 목록에 넣지 않아, 명령 읽기를 지난 푸시도 pre-push 훅이 막는다 |
| 훅 | 판이 다른 두 코어가 hooks 디렉터리 하나를 두고 서로 훅을 되돌려 양쪽 게시가 거부됐다 | 앞선 판의 훅도 하네스의 것으로 받고, 새 세션의 시작이 지금 판으로 바꾼다 |
| 오탐 | 프로젝트 안의 worktree(`.claude/worktrees/`)가 본 체크아웃의 커밋 안 된 변경으로 보여 푸시가 거부됐다 | 그 worktree는 바뀐 파일에서 뺀다. 그 자체로 트리다 |
| 명령 읽기 | `declare +x`·`typeset +x`·간접 `unset $v`·nameref가 `CLAUDE_CODE_CHILD_SESSION`을 지우는데 거부되지 않았고, 실제 푸시가 나갔다(`CLAUDECODE`에도 이전부터 있던 빈틈) | 두 이름 중 하나와 변수 내장 명령(`unset`·`export`·`declare`·`typeset`·`local`·`readonly`)이 한 명령에 있으면 거부한다. 쪼갤 수 없는 명령은 글자로 같은 검사를 한다 |
| 문서 | "처음 훅 전에 바뀐 하네스 파일은 보지 못한다"는 실제보다 넓었다(무시된 파일만 해당). 위 경로들이 한계에 없었다. `screen` 셸이 값을 물려받는 예외가 없었다 | 런북 §2·§5 |
| 공허한 변이 | 목록 밖 변이 4개가 모두 공허했다(훅마다 상태 재상속, 기준 HEAD, 정의 오류 때의 건너뛰기, 글자 검사의 변수 이름) | 그 코드는 없어졌다. 새 코드에 변이를 붙였다 |

이 세션(Claude Code 2.1.316, 클라우드)의 셸에 두 변수가 모두 있는 것은 확인했다 [확인]. Claude Code가 worktree에서 실제로 그 `cwd`를 보내는지는 문서로만 봤다 [문서]. 찾은 것마다 시험을 더했고, 시험 129개 + 실제 fsmap 1개, 변이 343개다(3라운드 반영 포함). 변이는 옮긴 코드로 41개를 다시 겨누고, 첫 설계의 8개를 빼고, 59개를 더했다. 다시 짠 설계의 독립 검증 결과는 아래에 적는다.

다시 짠 설계(aee20a4)에는 2라운드를 붙였다: 검증자 둘(반례 탐색, 주장별 판정·목록 밖 변이)과 판정자. 판정자는 작성자 주장 13건 중 10건이 맞고 2건이 반박됐다고 판정했다(critical·high 0). 첫 설계의 반박을 닫았다는 것은 장치와 시험 수준에서 지지됐다. 명령 줄의 푸시 경로는 검증자가 시도한 27꼴에서 막혔고 오탐도 없었다.

| 부류 | 찾은 것 | 고친 것 |
|---|---|---|
| 명령 읽기 (medium) | `env -vu`·`env --un`·`env --uns=`·`env --u`·`env -S'-u …'`(GNU env가 받는 옵션 묶음·긴 옵션 줄임·`-S`), 그리고 전개로 만든 이름(`unset CLAUDE_CODE_$x`)과 명령(`${u}set`)이 `CLAUDE_CODE_CHILD_SESSION`을 지우는데 거부되지 않았다. 뒤이은 스크립트의 푸시로 게이트를 지나지 않은 커밋이 실제로 나갔다. main 때부터 있던 빈틈이다 | env의 옵션을 GNU env가 읽는 대로 읽는다. 변수를 바꿀 수 있는 명령이 있으면 두 이름의 조각도 거부한다. 조각 없이 이어 붙인 이름은 명령 읽기 밖이라고 §5에 적었다 |
| 판정 범위 (low) | 형제 worktree를 `sed -i WT/f`·`cp`·리다이렉션·`git --git-dir/--work-tree`로만 바꾸거나, 같은 명령에서 만든 링크로 들어가면 그 worktree를 적지 않았다. 판정자가 커밋까지 해도 빠진다는 것을 더 찾았다 | 명령의 인자·리다이렉션 대상·`--opt=값`이 다른 worktree 안을 가리키면 명령 전에 그 worktree를 적는다 |
| 오탐 (low) | ref가 가리키지 않는 옛 커밋에 만든 worktree(bisect·비교)는 바꾼 것이 없어도 판정해 막았다 | 명령이 만든 worktree는 그 명령이 체크아웃할 커밋을 시작점으로 둔다 |
| 문서 (low) | 앞선 판 코어의 훅이 깔려 있는 동안 IDE 통합 터미널의 사람 푸시도 판정되는데, "판정하지 않는다"고만 적었다. dev 템플릿의 "모든 worktree"가 넓었다 | 런북 §1·§5, 스킬, 안내서, dev 템플릿 |
| 공허한 장치 (medium·low) | 목록 밖 변이 8개가 공허했다. 턴이 깨끗하게 끝난 worktree를 저장하지 않기, 정의 오류 때 worktree를 보지 않기, 글자 검사의 여러 줄 읽기 셋은 판정을 놓치게 했다. 나머지는 지운 worktree, `gh pr create`와 별칭의 게시 위치, 다른 레포가 만든 worktree, worktree 편집 검사의 디렉터리 | 일곱에 시험과 변이를 더했다. 하나는 같은 장치를 이미 다른 변이가 겨눈다 |
| CI | 고친 코드 때문에 기존 변이 하나가 컴파일되지 않아 CI의 변이 조각 하나가 실패했다(`mutation_error`) | 그 변이를 다시 겨누고, 모든 변이 목록이 코드에 맞는지(한 번만 나오고 컴파일되는지, 지정 시험이 있는지) 보는 시험을 더했다(약 11초) |

판정자가 남긴 미검증 하나: 병렬 훅의 상태 저장(H11)은 직접 다룬 검증자 항목이 없었다. 작성자 시험은 통과했다.

3라운드(마지막)는 고친 부분에 반례 탐색 검증자 하나를 붙였다. 고친 네 영역에서 게이트 우회는 찾지 못했다. 대신 오탐을 찾았다: 변수 내장 명령이 한 줄에 있으면 같은 줄의 다른 명령(`git grep`, 로그 파일 이름)이 두 이름을 말하기만 해도 거부했고, `CLAUDECODE_EXTRA` 같은 다른 변수의 온전한 이름도 거부해 런북과 어긋났다. 규칙을 좁혔다: 변수를 바꾸는 명령의 피연산자만 보고, 그 명령이 전개로 만든 이름을 바꿀 때(`unset $v`, nameref, `for v in …`)만 줄 전체를 본다. 고치면서 `read`·`printf -v`·`mapfile`도 변수를 비울 수 있는데 거부되지 않던 것을 찾아 닫았다(훅은 값이 비었는지만 본다). 읽기만 한 worktree도 적힌다는 것은 §5에 적었다. 2라운드에서 더한 경로 규칙이 `cd`·`git -C` 대상을 따로 적게 되어 그 두 변이의 지정 시험이 공허해졌다(CI가 inconclusive로 찾음). 지정 시험을 그 장치가 실제로 지키는 게시 시험으로 바꾸고, 변이 340개 전부를 지정 시험 하나씩으로 다시 돌렸다. 338개가 지켜졌고, 공허하던 둘(작업 디렉터리의 worktree 기록, 조각만 든 이름)은 그 장치만 지키는 경우를 시험에 더해 고쳤다. 이제 340개 모두 지정 시험이 실패한다 [확인].

3라운드 판정자는 검증자의 두 발견(오탐, 문서 불일치)을 확정했고, 좁힌 규칙(2815aee)에서 다시 돌려 그 오탐이 사라지고 검증자가 거부시킨 꼴은 그대로 거부되는 것을 확인했다(21/21, env 9/9, 허용 13/13, 시험 130개 통과). 그가 남긴 둘을 마지막으로 손봤다: 피연산자의 `NAME=값`은 nameref일 때만 값을 이름으로 읽는다(`export PATH=$PATH:/opt/CLAUDE_CODE_x/bin`이 거부되던 오탐), 경로로 읽는 단어 수 상한(200)을 1000으로 올리고 런북에 적었다. 이 마지막 손질은 라운드 상한(3) 뒤라 독립 검증을 받지 않았고, 시험과 변이(지정 시험이 실패함을 확인한 4개)로만 확인했다. 한 판정자는 우회 꼴을 새로 만드는 도중 응답이 안전 분류기에 막혀 멈췄다. 범위를 보고된 항목의 재실행으로 좁혀 다시 판정했다.
