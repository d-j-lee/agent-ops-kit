## 0. 결론

병렬 실행 수단은 네 가지이고, 각각 고유하게 잘하는 일이 다르다.

| 수단 | 고유한 장점 |
|---|---|
| 포크 | 같은 맥락에서 바로 갈라진다 |
| 새 서브에이전트 | 맥락을 물려받지 않아 판단이 오염되지 않는다 |
| 원격 자식 세션 | 컨테이너가 분리되고, 세션이 상주하며, 사람이 직접 들어갈 수 있다 |
| 로컬 CLI 프로세스 | 같은 파일시스템에서 설정(시스템 프롬프트, 도구, 모델, 권한)을 바꿔 띄울 수 있다 |

혁신 포인트는 하나를 고르는 데 있지 않다. 맥락은 같게, 판단은 다르게, 실행 환경은 깨끗하게 조합하는 데 있다.

### 기존 실험과의 관계

출처는 Probe C가 사용자의 이전 세션 대화 기록을 조사한 결과다. 모두 "기록에 그렇게 적혀 있다" 수준이다.

**이미 검증됨 [기록됨]**
- `create_session`(모델 지정 포함)
- 자식이 스킬과 CLAUDE.md를 받음
- `send_message` 우선순위:
  - `now`: 하던 도구가 끝난 뒤 턴을 중단(약 16초)
  - `next` / `later`: 턴이 끝날 때까지 대기
- 무인으로 끝까지 간 건 auto 모드뿐(default·acceptEdits 자식은 멈춤)
- `list_events`로 다른 세션 감시
- PR 구독으로 깨어나기
- 아티팩트 DB를 통신 버스로 쓰기
- Workflow로 병렬 검증

**이미 확인된 한계 [기록됨]**
- 승인을 기다리며 약 9시간 정지
- 리뷰 ↔ 개발 쓰레드 왕복은 실제로 쓰인 적 없음
- 세션 1개에서 $1,374.79
- `deniedMcpServers`가 클라우드 커넥터를 막지 못함
- `list_events`의 kinds 필터를 쓰면 빈 페이지가 나옴

**이번 세션에서 새로 측정한 것**
- 네 수단의 비교 매트릭스
- 포크의 맥락 상속과 비용(맥락 크기에 비례)
- 로컬 CLI 피어(포크, 피어 메시징, 세션 ID 충돌 H1)
- 자식 → 부모 응답이 진행 중인 턴에 주입되지 않는 pull 방식(H3)
- effort 미상속(H4)
- `--bg` 신뢰 게이트(H2)
- 예약 작업 지연(H7)

## 3. 활용안 (효용 × 실현성 순)

### P1. 블라인드 재현 후 대조 — 교차검증의 질을 바꾸는 방식
- **문제:** 지금의 "독립 에이전트 교차검증"은 대개 내 결론을 검토하게 하는 방식이다. 검토자가 내 결론에 끌려간다. 포크라면 맥락 전체를 상속하므로 더 심하다(H5).
- **방식:**
  1. 검증자에게는 결론을 주지 않고 질문과 원자료만 준다.
  2. 검증자가 독자적으로 결론을 낸다.
  3. 메인이 두 결론의 차이(diff)를 검토한다.
  4. 서로 다른 지점만 깊게 판다.
- **수단:**
  - 빠르게 할 때: 새 서브에이전트
  - 환경까지 독립시킬 때: 원격 자식 세션(별도 컨테이너에서 실제 재실행)
- **비용:** 원격 자식 1턴은 약 $0.27 + 작업량.

### P2. 클린룸 재현 게이트
- **용도:** 원격 자식 세션에 `source_url`을 주면 새 컨테이너에서 README, 설정, 테스트를 처음부터 그대로 따라 해 본다. 다음을 잡는다.
  - 문서와 실제의 어긋남
  - 내 컨테이너에서만 되는 상태
  - 숨은 의존성
- **근거:** 컨테이너가 분리되고 파일시스템을 공유하지 않으며, 막 부팅된 상태(uptime 0분)에서 시작한다 [확인].
- **확장:** 매일 새 세션으로 도는 예약 작업(`create_trigger`, `create_new_session_on_fire`)으로 야간 점검을 할 수 있다.

### P3. 상주 전문가 세션
- **방식:** 리뷰어, 아키텍트, 도메인 담당 등 오래 사는 원격 자식을 두고 `send_message`로 일을 맡긴다.
- **근거:**
  - 턴을 넘어 맥락이 유지된다 [확인].
  - 유휴 상태에서 1.5초 만에 일을 받고, 소규모 후속 턴은 약 $0.09다 [확인].
  - 사용자가 앱에서 그 세션에 직접 들어가 대화할 수 있다. 사람이 함께하는 에이전트가 된다.
- **필수 조건:**
  - 응답은 알림 큐로 꺼낸다(H3).
  - effort 공백이 있다(H4).
  - 이름과 태그 규칙을 둔다(H6).

### P4. 설정이 다른 쌍둥이 (로컬 CLI 포크)
- **방식:** `--resume <메인> --fork-session --session-id <새 UUID>`로 맥락은 같고 설정만 다른 별도 프로세스를 띄운다. 다음을 바꿀 수 있다.
  - `--append-system-prompt`(관점이나 페르소나)
  - `--allowedTools` 또는 `--permission-mode plan`(읽기 전용 쌍둥이)
  - `--model`(비용 등급)
- **효과:** 맥락 손실 없이 판단을 다양화한다. 같은 맥락에 페르소나만 다른 앙상블을 만들 수 있다.
- **근거:**
  - 포크 F와 G가 동작했다 [확인].
  - 피어 메시징이 양방향으로 됐다 [확인].
  - 비용은 회당 $0.3–0.4다(현재 맥락 크기 기준) [확인].
- **필수 조건:**
  - H1 대응(새 session-id, strip2, `< /dev/null`)
  - **사람이 붙어 있는 세션에서 사용자가 명시적으로 승인한 경우에만** 쓴다(H9). 무인 자동화에서는 분류기에 막힌다 [확인: R]
- **재현성:** H1 재현은 R에서 분류기에 막혀 이 컨테이너 1개에서만 관찰됐다(n=1).

### P5. 투기적 병렬 구현
- **방식:** 설계 대안 N개를 포크 N개가 `isolation: "worktree"`로 각각 구현한다. 메인이 테스트와 벤치마크로 고른다.
- **근거:** 파일시스템이 실시간 공유되므로 worktree 분리가 필수다 [확인]. 비용은 N × 부모 맥락이다 [도출]. 따라서 세션 초반이나 맥락이 가벼울 때 효율적이다.

### P6. 메일박스 규약 (세션 간 통신 표준화)
- **방식:** 자식 → 부모 메시지를 구조화된 JSON으로 고정한다.

  ```json
  {"task_id": "...", "status": "...", "artifact_ref": "...", "summary": "...", "evidence": "..."}
  ```

  부모는 체크포인트마다 `ReadNotifications`로 큐를 비운다. 오래 보관해야 하는 산출물은 GitHub 브랜치/PR이나 Artifact DB를 버스로 쓴다.
- **근거:** 응답이 pull 방식이고 턴에 주입되지 않는다 [확인]. 아티팩트 DB를 버스로 쓰는 방식은 사용자가 이미 검증했다 [기록됨]. 따라서 새로 정할 것은 메시지 스키마와 큐를 비우는 시점뿐이다.
- **이벤트 구동 루프:** 유휴 상태의 자식은 메시지를 받으면 새 턴으로 깨어난다 [확인: D]. 유휴 상태의 부모도 자식 메시지에 깨어난다 [확인: W 실험].
  - 측정 시각:
    - D 송신 15:51:56.29
    - 서버 큐 적재 15:52:02
    - 부모에 "대기 알림 있음" 시스템 이벤트 도착, 새 턴 시작
    - `ReadNotifications`로 내용 획득 15:52:05.6
    - 송신부터 내용 획득까지 약 9.3초
  - 깨우는 신호는 push로 오고, 메시지 내용은 직접 꺼내야 한다(pull).
  - 따라서 **부모가 폴링 없이 턴을 끝내고, 자식 보고가 오면 다시 깨는 리뷰 → 개발 자동 루프가 성립한다**(이전 세션의 열린 질문). 표본은 1건이다.

### P7. 정원사 세션 — 생태계의 자가 진화와 자정
- **방식:** 주 1회 새 세션으로 도는 예약 작업이 다음을 한다.
  1. 최근 세션들의 대화 기록(`list_sessions` / `list_events`)에서 교훈, 반복 실패, 미해결 항목을 뽑는다.
  2. 지식 레포에 PR로 올린다.
  3. 종료된 프로브 세션의 보관 후보를 보고한다. 보관 자체는 사용자가 확인한 뒤에 한다.
- **근거:** 새 서브에이전트가 다른 세션의 기록을 읽고 요약할 수 있음을 이번에 실행했다(Probe C).
- **선행 조건:** 영구 저장소가 필요하다(레포 또는 Drive).
- **위험:** 다른 세션의 기록은 신뢰할 수 없는 데이터다. 그대로 지식 레포에 올리면 다음 세션의 CLAUDE.md로 이어지는 주입 경로이자 비밀 유출 경로가 된다. 사람의 PR 검토와 비밀 필터링을 필수 단계로 둔다.

### P10. 비용 상한 장치 (V 지적 반영)
- **문제:** 세션 하나에 $1,374가 든 전례가 있다 [기록됨]. 자식도 create_session을 갖고 있어 재귀적으로 퍼질 수 있다 [확인].
- **방식:** 위임할 때마다 예산을 명시하고, 결과에 cost_usd를 보고하게 하며, 재생성 금지를 기본값으로 둔다. 정지 감지기(P9)가 누적 비용도 함께 감시한다.

### P9. 정지 감지기 — 9시간 정지를 막는다
- **문제:** 이전 세션에서 자식이 승인을 기다리며 약 9시간 멈췄다 [기록됨]. `status_bucket`과 `post_turn_summary.needs_action` 필드가 있다는 것은 [확인]. 승인 대기가 실제로 BLOCKED로 나타나는지는 [미확인]이다. BLOCKED 값은 아직 관측하지 못했다.
- **방식:**
  1. 프로젝트 태그가 붙은 자식들을 주기적으로 조회한다.
  2. BLOCKED 상태이거나 오래 업데이트가 없는 세션을 찾는다.
  3. PushNotification으로 사용자 폰에 알린다.
  4. 자식은 auto 모드로만 띄운다 [기록됨: 다른 모드는 멈춤].
- **수단:** 조율 세션 안의 루프, 또는 매시간 새 세션으로 도는 예약 작업. 부모 대화가 빠르게 길어지는 것을 피하려면 예약 작업 쪽이 낫다 [추론].

### P8. 느린 외부 상태 감시
- **용도:** CI, 배포, 리뷰 대기처럼 분 단위로 바뀌는 상태만 `send_later` / 예약 작업으로 감시한다(H7).
- **보완:** 초 단위가 필요하면 Monitor나 백그라운드 Bash 같은 로컬 수단을 쓴다.

## 4. 바로 쓸 운영 규칙

1. **맥락이 필요하면 포크, 판단이 필요하면 새 서브에이전트, 환경이 필요하면 원격 세션, 설정이 필요하면 로컬 CLI.**
2. **검증은 포크로 하지 않는다.** 블라인드 재현으로 하고, 결론을 숨긴 채 원자료만 준다.
3. **포크는 일찍 쓴다.** 맥락이 커지면 새 서브에이전트에 정확한 프롬프트를 주는 쪽으로 바꾼다.
4. **"delivered"는 받았다는 뜻이 아니다.** `ReadNotifications`나 `list_events`로 실제 수신을 확인한다.
5. 로컬 `claude` 재실행은 **기본적으로 금지한다**.
   - 사용자가 그 명령을 직접 승인한 경우에만 다음을 모두 갖춰 띄운다:
     - `--session-id $(uuidgen)`
     - 원격 환경변수와 자격증명 환경변수(GH_TOKEN, GITHUB_TOKEN, CLOUDSDK_AUTH_ACCESS_TOKEN) 제거
     - plan 모드
     - `< /dev/null`
   - 이번 실측은 자격증명을 가진 채 auto 모드와 `--permission-prompts none`으로 돌았다. 이렇게 띄운 에이전트는 claude.ai 화면에 보이지 않는다.
6. 원격 자식은 **제목 접두어와 태그**를 붙이고, 끝나면 보관 후보로 보고한다.
7. 원격 자식은 effort를 상속하지 않는다. 품질이 중요한 위임이면 이 점을 감안한다.

## 5. 미확인 / 다음 실험

- H1 해결에서 결정적이었던 것이 `--session-id`인지 환경변수 제거인지 구분하지 않았다.
- 원격 자식 세션을 손자 단계(depth 2 이상)까지 만들 수 있는지, 동시 생성 한도는 얼마인지 측정하지 않았다(lineage limit 8은 기록상 값).
- 사용자가 UI에서 자식 세션의 effort를 바꿀 수 있는지 확인하지 않았다.
- (해결) 유휴 상태의 부모는 자식 메시지에 깨어난다. W 실험, 송신부터 내용 획득까지 약 9.3초, 표본 1건.
- 진행 중인 턴에서는 원격 알림이 자동으로 주입되지 않는다. 턴 안에서 자동으로 꺼내 주는 장치가 있는지는 [미확인]이다.
- 포크가 자기 백그라운드 작업의 완료 알림을 받기까지 약 20분 지연됐다(포크 B 관측). 원인은 [미확인]이다.
- `--input-format stream-json`으로 오래 사는 로컬 워커를 만드는 방식은 시도하지 않았다.
