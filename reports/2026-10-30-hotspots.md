## 1. 결론

Rust 코드를 쓰는 것이 첫 단계인 후보는 없었다 [도출: 아래 세 후보 각각의 원인 측정에서]. 원인은 반복 파싱, 매번 다시 짓는 색인, 화면 스레드에서 도는 계산처럼 언어와 무관했다. 첫 단계에서 쓴 Rust는 이미 만들어진 도구(orjson, ruff, oxlint, uv)였다.

## 2. 후보 1 — work-atlas 훅 지연

훅은 Claude Code의 편집·프롬프트마다 새 Python 프로세스로 돈다. 질의 계산은 수 ms였고 시간은 매 호출의 준비 작업에 갔다 [확인: cProfile, `python -X importtime`].

| 원인 | 비용(근사) |
|---|---|
| 역할 매핑이 비어 있어도 매 호출 17KB 코드북 YAML을 순수 Python으로 파싱 | 수십 ms |
| 훅이 쓰지 않는 `jsonschema` import | 약 53ms |
| 텍스트 색인(ZK 9.6MB)을 질의마다 두 번 다시 지음 | ZK에서 수백 ms의 절반 |
| JSON 읽기가 표준 `json` | ZK 색인 로드 약 230ms → orjson 약 78ms |

**1단계(Python 그대로, 3개 파일 +30/−8줄)** 결과. 번갈아 측정한 중앙값이다.

| | 수정 전 | 수정 후 | 등급 |
|---|---|---|---|
| 편집 훅 LANG · ZK (21회) | 190 · 192ms | 101 · 110ms | [확인] |
| 프롬프트 훅 LANG · ZK (21회) | 340 · 636ms | 197 · 393ms | [확인] |
| 편집 · 프롬프트 훅 ZK, `diffcheck --timing 11` (2026-10-31) | 143 · 501ms | 82 · 305ms (-42% · -39%) | [확인] |
| ZK 전체 빌드(같은 `--as-of`, 번갈아 3회) | 18.2~18.8초 | 14.1~14.4초 | [확인] |
| 독립 검증자의 재측정 | 편집 -41~-44%, 프롬프트 -36~-40%, 빌드 17.0~17.1 → 13.8~14.2초 | | [기록됨] |

측정마다 절대값이 10~20% 흔들렸고, 몰아서 잰 측정까지 합치면 편집 훅 비율은 -32%~-50% 범위였다 [확인].

회귀 확인 [확인]: 훅 출력 4종(편집·프롬프트 × 두 레포) 동일, 같은 `--as-of`로 지은 모델 파일 5개 바이트 동일, 테스트 277개 통과(orjson이 있을 때와 없을 때 모두). 패치는 work-atlas 규칙에 따라 PR로 올렸다: https://github.com/d-j-lee/work-atlas/pull/1 (CI 3/3 통과, 병합은 소유자).

**2단계(Rust 질의 프로토타입 `atlas-sim`).** 같은 색인 파일에서 실제 질의 4종, 합성 다국어 질의 13종, 반올림 경계 값 13,048개 색인 모두 Python과 결과가 같았다 [확인]. 프로세스 단위로 LANG 약 220 → 55ms, ZK 약 330 → 135ms였지만 차이의 대부분(150ms 안팎)은 Python 기동과 import였다. 같은 프로세스 안의 색인 읽기와 질의만 비교하면 ZK 약 130 → 105ms다 [확인]. 그래서 PyO3로 훅에 붙이면 이득이 작다 [도출]. 다음 단계는 질의용 색인을 build 때 저장하는 형식 변경이다 [추론].

## 3. 후보 2 — docbench 문서 비교

| 시나리오(4,334줄) | jsdiff(현재) | Rust → WASM(V8, JSON 왕복 포함) |
|---|---|---|
| 가벼운 수정 | 19ms | 33ms(복사 비용으로 오히려 느림) |
| 줄 40%를 다시 씀 | 3.6초 | 0.72초 |
| 문단 재배치 + 30% 재작성 | 4.0초 | 0.50초 |

[확인: 이 세션 측정. 검증자 재측정은 jsdiff 3.89 · 4.32초, WASM 0.65 · 0.39초 [기록됨]]

- 원인: 줄 단위 Myers diff와 바뀐 줄마다 도는 낱말 diff가 화면 스레드에서 돈다. jsdiff의 낱말 토크나이저는 한글을 단어 문자로 보지 않아 한글을 글자 하나씩 토큰으로 쪼갠다 [확인: jsdiff 9.0.0 소스와 출력].
- 1단계: Web Worker로 옮기면 화면은 멈추지 않는다 [추론]. jsdiff의 `timeout(200)`·`maxEditLength(1000)`은 각각 약 200ms·100ms 만에 포기하고 `undefined`를 돌려주므로 대체 화면이 필요하다 [확인].
- 2단계 WASM의 동일성: 더한·지운 줄 수 9/9, 줄 목록 6/9, 낱말 강조까지 3/9가 jsdiff와 같았다. 나머지는 크기가 같은 다른 최소 diff다. 무작위 입력 4,000쌍에서는 줄 수 100%, 줄 목록 99%, 낱말 분할 86%가 같았다 [확인]. 처음 보고에는 "화면에 그릴 줄 목록이 6개 경우에서 같다"고만 써서 비교 범위보다 넓게 읽혔고, 독립 검증이 이를 잡았다(§5).

## 5. 회귀검증이 스스로 속은 경우 → ⑦

| 함정 | 무엇이 있었나 | 지금의 장치 |
|---|---|---|
| 빈 출력끼리 비교 | 측정 스크립트가 세션 ID를 재사용해, 편집 훅이 두 번째 실행부터 아무것도 내지 않았는데도 "동일"을 찍었다. 2026-10-31 `diffcheck`로 다시 돌리면 같은 ID에서 첫 번째는 `empty`(기준 306바이트, 후보 0바이트), 두 번째도 `empty`(둘 다 0바이트)로 실패한다 [확인] | `diffcheck`의 빈 출력 실패, `{nonce}` |
| 비교 범위보다 넓은 주장 | 위 §3 | 보고에 투영을 적는다, 무작위 입력 |
| 비결정성 | `--as-of` 없이 지은 두 빌드의 `categories.json`이 `as_of`와 `age_h_p50`에서 달랐다 [확인] | `--determinism`, 시각 고정 |
| 의미가 다른 대체 구현 | orjson이 NaN·Infinity·1e400·짝 없는 서로게이트·깊은 중첩을 거부하고, 64비트 밖 정수를 float로 읽었다. 기존 테스트 277개는 그대로 통과했다 [기록됨: 독립 검증자 실험]. 거부되는 입력은 표준 `json`으로 다시 읽게 고쳤고 경계 입력 대조가 원본과 같아졌다. 64비트 밖 정수만 남는다(문서화) [확인] | 경계 입력표 |
| 수치 이식 경계 | Rust 이식이 반올림 경계에서 Python과 달랐다. 반올림 방식(0.00035 → 0.0004 대 0.0003), 실수 파싱 1 ULP(경계 값 13,048개 중 1,159개). 둘 다 고친 뒤 0개 [확인] | 일부러 만든 경계 값 |
| 실패를 결과 없음으로 | 잘못된 경로를 주자 비교 스크립트가 "찾은 것 없음"으로 보고했다 [기록됨] | 도구 실패는 종료 코드 2 |
| 측정 잡음 | §2 | `--timing`(번갈아), 범위 보고 |
